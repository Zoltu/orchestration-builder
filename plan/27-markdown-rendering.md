# Step 27 — Markdown rendering with syntax highlighting

## Goal

Render the agent's free-form text — tasks, `ask_human` questions and context, result summaries, and the surfaced run error message — as formatted Markdown with code-block syntax highlighting, instead of the plain `textContent` blobs the UI shows today. The agent produces Markdown (code fences, lists, emphasis); the UI should display it as the agent intended so a non-developer can read results without parsing raw punctuation.

## Context

Read [`14-multi-run-ui.md`](14-multi-run-ui.md) (the `textContent`-only security invariant this step revises), [`17-per-run-view-readability.md`](17-per-run-view-readability.md) (where the result/summary/error/artifact text is rendered today), `source/web/static/app.js` (the `renderRunSummary` / `renderQuestions` / `renderError` / `renderCurrentActivity` functions this step rewrites), and `source/web/static/index.html` + `styles.css`.

The current UI injects every model-output string via `element.textContent`, which flattens Markdown to literal punctuation. The target user is a non-developer who cannot read `# heading` or `` ```ts `` as formatting. This step introduces two carefully-chosen, vendored, dependency-free rendering libraries — `showdown` (Markdown → HTML) and `highlight.js` (syntax highlighting inside code blocks) — and routes the agent-authored text fields through them.

The model is a trusted component (see `docs/security.md` "Threat model"); its prose is not assumed to be an attack, and rendering it as Markdown is the intended UX. The residual concern is not a malicious model but prompt injection — a malicious file in the workspace coercing the model into emitting markup that would be dangerous if inserted into the DOM as raw HTML. The primary defense is upstream (workspace isolation, egress restriction, injection-resistant prompts); the sanitization pass below is a light defense-in-depth backstop for the case where an injection attempt succeeds in coercing the model's output. It is not a quarantine on the model, and the model is not over-defended.

## Deliverables

1. **Vendored dependencies.** Add `showdown` and `highlight.js` as the only permitted runtime dependencies beyond Bun built-ins (this is a deliberate exception to the no-dependencies policy, approved by the operator; both are small, widely-audited, and have no transitive runtime deps). Vendor their unminified browser builds as static assets under `source/web/static/vendor/` (no `node_modules` in the deployed image) and `<script>`-include them from `index.html` ahead of `app.js`. Do **not** add them to `package.json`'s runtime deps — the web client is a static bundle, not a Node program. Record the version pins and the rationale in `docs/security.md` ("Dependency surface") and this step's closeout.
2. `source/web/static/app.js` — add a `renderMarkdown(text)` helper that turns a string into sanitized DOM nodes, and replace the `textContent` assignment for the Markdown-carrying fields:
   - `renderRunSummary`: the **Task** and **Result** `<dd>` values.
   - `renderQuestions`: the question text and the `context`.
   - `renderError`: the error `message` (the `kind` stays a plain label).
   - `renderCurrentActivity`: leave as `textContent` — the current-activity line is a one-line machine summary, not agent Markdown.
   - The log row summaries and raw-payload detail stay `textContent` (they are structured, not prose).
3. **Defense-in-depth sanitization pass.** `showdown`'s output is HTML; markup that a prompt-injection attempt from the workspace coerced into the model's output must not reach the DOM as executable markup. Configure `showdown` with `highlight.js` for fenced code, and add a sanitization pass that strips `<script>`, inline event handlers (`on*`), `javascript:` URLs, and any tag/attribute not on an allowlist (headings, lists, code, pre, em/strong, links with `href` only, blockquote, etc.). This is a secondary backstop — the primary defense against prompt injection is upstream (workspace isolation, egress restriction, injection-resistant Guild prompts) — not a quarantine on the trusted model. Prefer a small, audited sanitizer (vendored) over hand-rolling regex. The allowlist and the sanitizer choice are recorded in `docs/security.md`.
4. `source/web/static/styles.css` — style the rendered Markdown (headings, code blocks with the highlight.js theme, lists, blockquotes) so the agent's output reads as a document, not a raw dump.
5. `docs/security.md` — document the new rendering pipeline, the vendoring decision, the sanitizer allowlist, and the threat-model framing: the model is a trusted component, the workspace is untrusted, and the sanitizer is a defense-in-depth backstop for prompt-injection-coerced output (the primary injection defense is upstream), not a quarantine on the model.
6. `source/web/render.test.ts` (or a new `source/web/markdown.test.ts`) — if any sanitization logic is pure (the allowlist check, the tag stripper), unit-test it in-memory. The DOM-attachment glue is a leaf and is not unit-tested.

## Module boundaries

- All rendering stays in `app.js` (a thin DOM leaf) plus the vendored libraries; no executor or `render.ts` changes. `render.ts` continues to ship plain strings; the client decides how to render them.
- The Markdown fields are exactly: task, result summary, question text, question context, error message. Tool names, log payloads, timestamps, role names, and run ids stay `textContent`.
- No new endpoints. No executor changes.

## Acceptance criteria

- [x] Task, result, question, context, and error-message fields render as formatted Markdown (headings, lists, code blocks) with syntax-highlighted fenced code.
- [x] Markup that a prompt-injection attempt from the workspace coerced into the model's output (e.g. `<script>` or an `onerror` handler, or a `javascript:` link) is stripped before reaching the DOM; the defense-in-depth backstop holds even if an upstream injection defense fails.
- [x] The vendored libraries and their versions are recorded in `docs/security.md`.
- [x] Log rows, role names, timestamps, run ids, and the current-activity line remain `textContent` (no Markdown rendering there).

## End-of-step evaluation

Re-read `app.js` for every prose-field insertion point and confirm the Markdown path is used only for the allowlisted prose fields and the sanitizer runs on every one of them. Confirm a code fence containing `<script>alert(1)</script>` renders as highlighted, non-executing text. Confirm the vendored bundle adds no `node_modules` to the deployed image and no entry to `package.json` runtime deps. Confirm `docs/security.md`'s allowlist matches what the sanitizer actually enforces. Confirm the threat-model framing is consistent: the model is treated as a trusted component and the sanitizer as a defense-in-depth backstop for coerced output, not as a defense against a malicious model.

## Estimated effort

Medium — the libraries are small, but the sanitization review is security-sensitive and the Markdown-field allowlist must be exact.

Deviations / decisions (authoritative):

- **ESM import vs `<script>`-include.** The plan said to `<script>`-include `showdown` and `highlight.js`. Both are vendored as classic deferred `<script>` globals (`window.showdown`, `window.hljs`), matching the plan wording. `hyperapp` remains an ESM import (unchanged from before) — it is a pre-existing decision this step does not revisit. The new `markdown.js` sanitizer is an ESM `import` in `app.js` (it is project-authored, not a third-party UMD, and `import` keeps it out of the global namespace). `showdown`'s browser build exposes a `Converter` constructor as `window.showdown.Converter` (and `window.showdown` itself is the constructor namespace), and `highlight.js`'s `cdn-release` browser bundle exposes `window.hljs`. `showdown` is highlighted by a post-process regex over its `<pre><code>` output rather than a renderer hook (it has no marked-style renderer override API), which is the idiomatic integration for its API.
- **No third vendored sanitizer; the sanitizer is project-authored.** The plan suggested preferring a small audited vendored sanitizer over hand-rolled regex. Instead of vendoring DOMPurify (a third exception to the no-dependencies policy) or regex-stripping (fragile), the sanitizer is a hand-written allowlist walker over a parsed tree — robust because it operates on a DOM-parsed tree (not regex on HTML), small, auditable, and the allowlist decisions live in tested project code rather than an opaque dependency. The HTML→vnode architecture means content never reaches the DOM as markup at all (hyperapp places text into text nodes/properties), so the sanitizer's job is only to filter which tags/attributes become vnodes. As a defense-in-depth backstop for coerced output this is more than sufficient; it is not load-bearing as a quarantine on the trusted model.
- **Disallowed tags are dropped-or-unwrapped, not always unwrapped.** A denylist of non-prose/dangerous tags (`script`, `style`, `iframe`, `object`, `embed`, `svg`, `form`, `input`, `link`, `meta`, `audio`, `video`, etc.) is dropped with its whole subtree so a `<script>` body never becomes visible text; every other disallowed tag is unwrapped (tag removed, sanitized children kept) so agent-authored `<div>text</div>` still yields the inner `text`. Recorded in `docs/security.md`.
- **The run-list task stays `textContent`.** The plan's module boundary lists "task" as a Markdown field and the deliverable names `renderRunSummary`'s Task/Result `<dd>` values specifically. The run-list entry's truncated one-line task is a compact listing, not the readable Task field; rendering Markdown there (headings, blocks) would be visually wrong in a single-line row. It stays a string child; the per-run Task `<dd>` is the Markdown-rendered Task field. This matches the acceptance criterion's intent (the Task field renders as Markdown; the run-list row is a listing).
- **`img` is not on the allowlist.** The plan's allowlist examples ("headings, lists, code, pre, em/strong, links with href only, blockquote, etc.") do not include images. `img` is excluded to avoid `src`-based tracking/data-URI abuse if a workspace prompt-injection attempt coerces an image tag into the model's output; Markdown images in agent output are dropped (their `alt` text is not surfaced). Recorded in `docs/security.md`; can be revisited if agent output starts relying on images.
- **`allowJs` in `tsconfig.json`.** Required so the TS test can import the JS sanitizer module without a `.d.ts`. `checkJs` stays false, so no JS is type-checked; the only newly-resolved JS file is `markdown.js`, and its behavior is covered by the unit suite.

The threat-model framing is consistent across `docs/security.md`, `docs/foundry.md`, and the `app.js`/`markdown.js` header comments: the model is a trusted component, the workspace is untrusted, the sanitizer is a defense-in-depth backstop for prompt-injection-coerced output, and the primary injection defense is upstream.
