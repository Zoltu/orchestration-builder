# Adaptive Orchestrator — Development Plan

This is the working development plan for the Adaptive Orchestrator. It is broken into **bite-sized steps**, each sized to be completed in a single session by a competent agent. The foundation (the original Phases 1–4) is already complete; its design-decision record lives in [`00-foundation-completed.md`](00-foundation-completed.md). The executable work begins at step `01`.

> **Note:** This plan is a living document. No plan survives contact with reality unchanged. When implementation reveals that a plan's assumptions are wrong, or that a different approach is clearly better, update the plan (and `AGENTS.md`) to match the well-factored code, not the other way around. See `AGENTS.md` ("Adapting the Plan").

## How to use this plan

1. Read [`AGENTS.md`](../AGENTS.md) first and last. Its Project-Wide Principles, type-safety, error-handling, testing, and architecture rules apply to every step.
2. Read [`00-foundation-completed.md`](00-foundation-completed.md) for the design-decision context inherited from Phases 1–4.
3. Pick the lowest-numbered step that is not yet complete. Each step file is self-contained: goal, context, deliverables, module boundaries, acceptance criteria, and (where relevant) operator handoff.

## Step hygiene — read before starting any step

Every step must leave the repository in a **clean, healthy state**. A step is not done when its acceptance criteria pass; it is done when the repository is something a reviewer would be happy to inherit.

- **Leave it clean.** `bun run typecheck` and `bun test source/` must both pass at the end of the step. No failing tests, no type errors, no dead code introduced, no TODO litter left behind.
- **Keep the plan out of source.** Source files, tests, and commit messages must never reference the plan — no "step N", "phase N", "the plan", or `plan/` paths in comments, identifiers, error messages, or test names. The plan is a transient artifact that will be deleted once the work is complete; source must stand on its own. Comments that need design context point at the permanent `docs/*.md` by filename and section; comments that need a sibling module point at its path or symbol, not at the step that builds it. See `AGENTS.md` "Comments".
- **Re-check comment and newline hygiene.** Before declaring a step done, re-read the changed files against `AGENTS.md` ("Comments explain why, never what" and "Formatting"): delete comments that restate a name/signature/type/obvious behavior, remove bare `TODO`/`FIXME`/`XXX`/`HACK`/"later"/"placeholder" notes (move real work to the [Tracked technical debt](#tracked-technical-debt) table), and rejoin any comment, doc block, or string literal broken mid-sentence for width. These accumulate silently; sweep them every change.
- **Pay technical debt before closing.** If the step accrued debt that can be paid within the session (a cast, a control-flow-via-catch, a missing guard, a duplicated helper), pay it before the step closes. Do not defer debt that is cheap to remove.
- **Track debt you cannot pay.** If some debt is genuinely unavoidable (e.g. it depends on a later step's deliverable), record it explicitly in this README's [Tracked technical debt](#tracked-technical-debt) table, name the step that will remove it, and update that step's file to call out the removal work. Untracked debt is a violation.
- **Evaluate and refactor at the end.** Before declaring a step done, re-read the changed files and the modules they touch. Is the naming clear? Is the data flow obvious? Did a helper drift from its siblings? Refactor while the context is fresh. Small refactorings at the end of each step keep the codebase healthy across the whole plan; they are not optional polish.
- **Update the plan when reality diverges.** If a discovery during a step will require significant work to overcome, **insert a new step** into the plan and renumber the affected steps accordingly. Renumber both the status table below and the step filenames (`NN-name.md`). Do not silently expand a step's scope; split it.
- **Keep steps session-sized.** If a step grows past what a single session can do well, split it into two steps and renumber. Code quality over speed — see `AGENTS.md`.
- **External actions need operator handoff.** Any work that cannot be done inside this environment (Docker builds, network egress, installing a system tool) must end the step with a clear **Operator handoff** section telling the operator exactly what to run and what success looks like. The in-environment portion (code, in-memory tests, typecheck) must still be complete and green before handoff. The agent must also surface the handoff **prominently in its final response** — a dedicated, hard-to-miss "Operator action required" block at the end, not a line buried mid-summary. The operator only reads the final message; if the action is not flagged there, it will be missed. Note that a real-LLM end-to-end run is **not** automatically operator-only: see `AGENTS.md` ("Local test model") — the local Ollama endpoint usually lets a step exercise its real-LLM smoke test in-environment first. Only things the local model cannot exercise (multi-container Docker builds, real network egress, hardware the sandbox lacks) still require handoff.

## Project goals (recap)

1. Build a minimal executor that runs a small language model against a JSON-driven Guild configuration. *(done — foundation)*
2. Seed a Guild capable of long-horizon coding tasks and project maintenance for non-developers. *(done — foundation; refined as tools land)*
3. Validate the system with a real benchmark suite covering minutes-long bug fixes and days-long application builds.
4. Add a meta-optimizer (Foundry) that automatically improves the Guild offline.
5. Deliver a simple web UI and containerized deployment for end users.

The target user is a **non-developer**. The Guild must ask few, clear clarifying questions and explain failures in plain language.

When a step completes, mark its status `✅ complete` and add a dated closeout section to its file (see `00-foundation-completed.md` for the format) recording any deviations from the plan wording, so future sessions inherit reality rather than aspiration.

## Implementation order

The plan is structured around the product vision: a Docker image that serves a webpage, left running 24/7, with all user interaction through the UI; the Foundry builds against this target as an API client, never touching the executor bespoke. The ordering enforces "fully functional executor before any real Foundry work."

- **Steps 01–05** close out the original Phase 5 (integration & smoke testing) and add the missing v1 tools: `write_file` (01), the CLI (02), an in-memory e2e test (03), and the two safe checker tools `typecheck` (04) and `test` (05).
- **Steps 06–09** build the benchmark suite (original Phase 6).
- **Steps 10–12** build the web UI backend and the transitional `--serve` wiring (original Phase 8). Step 12 is committed but has tracked debt (server teardown, missing `SIGTERM`, dead-server UX) removed by steps 13–14.
- **Step 13** turns the executor into the long-running service backend it must be as PID 1: one-project, one-task-at-a-time, no queue, task submission via a JSON API (`POST /api/runs`), proper `SIGINT`/`SIGTERM` handling, no teardown on run completion. This is the deployment substrate and the Foundry's API target. (Split from the UI rewrite — a different kind of work — so the step stays session-sized.)
- **Step 14** rewrites the web client into the multi-run UI (run list, create-run form, per-run view with switching, dead-server surfacing) that step 13's API requires, and removes the client-side half of the step-12 debt.
- **Step 15** packages the service as a Docker image (one container = one project, single writable `/workspace` mount, `ENTRYPOINT ["bun","source/serve.ts"]` with no arguments — all configuration is environment variables with production defaults). The executor modifies the workspace in place and writes run bookkeeping under `<workspace>/.orchestration/`. The image build runs `bun install`, typecheck, and tests as gates, then removes `node_modules`.
- **Step 16** is an operator-collaboration step that figures out what UI features should exist beyond the step-14 minimum, creating follow-up steps as needed. Its closeout (2026-06-23) agreed five UI feature steps (17–21) and inserted them here; a follow-on operator proposal (also 2026-06-23) added the effort channel (steps 23–24) and reclassified the run-interrupt channel as v2.
- **Steps 17–21** build out the web UI beyond the step-14 minimum: step 17 makes the per-run view readable (human-readable log, error surfacing, artifacts, current-activity indicator); step 18 improves `ask_human` UX (arrival notification + past Q&A history); step 19 adds full-log access (pagination + export) — ✅ complete (2026-06-24); step 20 surfaces budget & elapsed-time display — ✅ complete (2026-06-24); step 21 adds re-run-a-past-task and a read-only config/about panel — ✅ complete (2026-06-24). Each is client + `render.ts`, with small backend touches only where a new endpoint or additive log field is needed.
- **Step 22** adds the executor role-tree log events, removing the step-11 role-activity debt. It also enriches `log.jsonl` with the full LLM request/response and tool-call/tool-result detail (sent messages, received assistant content + tool calls, raw tool arguments, full un-truncated tool results) so a reviewer can reconstruct exactly what the model did, and renders those paired details in the UI's raw-payload toggle — folding in the log-richness and raw-pairing feedback deferred from step 17.
- **Steps 23–24** add the effort channel — a per-run, project-wide speed-vs-quality setting (integer 0–5 with quality-graded labels). Step 23 is the executor channel (persistence in `.orchestration/settings.json`, threading through `RunOptions`/`RunMeta`, injection into the entry role's context, the `POST /api/runs` effort field, and `GET|PUT /api/settings`) — ✅ complete (2026-06-25); step 24 is the UI slider — ✅ complete (2026-06-25), shipped as a single effort slider in the create-run form whose `onchange` saves its position as the default for the next run (per operator direction; an earlier two-slider draft was rejected as redundant). The executor provides the channel only — the effort→behavior mapping lives in the Guild prompts (step 25) so the Foundry can later tune it. Lands before the seed-Guild buildout so prompts are written against the real channel.
- **Steps 25–29** are the Guild build-out, the Markdown/UI polish, and the retrospective: step 25 writes/refines all role prompts against the real executor surface (including teaching the planner and orchestrator to branch on the effort directive injected in step 23) and iterates with the operator — ✅ in-environment complete (2026-06-25): all six prompts rewritten, effort-branching validated against the local Ollama model (effort 1 → `orchestrator→coder`; effort 5 → `orchestrator→planner→coder`), `bun run typecheck` and `bun test source/` green; **operator sign-off on real-world tasks still pending**. `run_shell` is step 30's deliverable and is deliberately not taught/wired in step 25; step 27 renders the agent's Markdown (tasks, questions, results) with syntax highlighting via vendored `marked` + `highlight.js` (a deliberate, operator-approved exception to the no-dependencies policy) — ✅ complete (2026-06-26); step 28 is the UI polish design pass over the functional UI — ✅ complete (2026-06-26): a cohesive token-based visual system, a responsive sticky-sidebar layout with the active run as the focal point, and two trusted-structure class hooks (`is-active`, `is-busy`); no executor/render/server changes, no new untrusted-content paths (operator browser sign-off pending). Step 29 is the brainstorm that decides whether follow-up steps are needed before `run_shell` and the Foundry — ✅ complete (2026-07-21): beyond the UI redesign sub-plan (below), the Guild retrospective inserted step 32 (cross-role compaction write half) and step 34 (`researcher` role) before the Foundry, fixed a stale `agent`-`budget` claim in `orchestrator.md`, and — at the operator's direction — implemented the specialized review pipeline in-session (retired `critic`; added `architecture`/`style`/`security`/`acceptance` lead+reviewer pairs running clean-eyes/warm-judge loops capped 1/3/5 by effort; orchestrator rewritten to route-and-kick-off; validated by three real-LLM smoke runs), recorded two deliberate decisions (checker timeout stays 30s; reviewers stay read-only) plus the Foundry-shaped deferrals — see the step file's closeout. The executor is frozen at step 25 — only `guild/`, `source/web/`, and the seed-guild conformance test change in 25–29. (The run-interrupt channel is **v2** — it does not exist when step 25 runs; the buildout does not teach interrupt handling, deferring it to step 31.)

The step-29 brainstorm produced a **UI redesign sub-plan** at [`plan/ui/PLAN.md`](ui/PLAN.md): a flow-graph run view to replace the development-iteration panel UI. It is **fixture-first, backend-last**: phase A (steps 01–11) nails the visualization against a rich set of mock run snapshots and a dev playback harness — no backend changes, instant iteration on every scenario (retry, pending question, error, deep delegation); phase B (steps 12–17) adds the guild human-facing label/description schema (12), the server-side `InteractionModel` adapter + `/api/runs/:id/flow` endpoints (13), swaps the fixture data source for the live endpoint (14 — a data-source swap, not a rewrite, because phase A rendered the exact contract step 13 produces), wires the visualization tooltips onto live data (15), and retires the legacy panels (16). Step 17 (deferred) adds token-level flow via streaming/`llm_call_start`, gated on the step-30 executor unfreeze. (Phase B was renumbered into execution order on 2026-07-09; see `plan/ui/PLAN.md`.) The sub-plan is self-contained and does not renumber the main plan; its phase-A web-only steps may proceed in parallel with the main plan's executor track (30–33).

**Executor change during the step-13 freeze (2026-07-10):** the executor is nominally frozen at step 25, but a real-LLM smoke test against `llama-server` (the bundled guild's target) surfaced a compatibility bug that blocked *any* run against strict-template endpoints. `buildInitialHistory` emitted the entry role's effort directive as a **second `system` message** after the system prompt; many model chat templates (Gemma-family and others, including the available "Agents A1" model) reject a `system` message that is not the first message, so the endpoint returned `400 Jinja Exception: System message must be at the beginning` before any `llm_call` landed. The fix merges the effort directive into the single system message (`systemPrompt + "\n\n" + directive`) rather than emitting a second one — the directive text still reaches the entry role so prompts branch on effort, but the wire format is one `system` message, compatible with strict templates. `engine.ts` + one `engine.test.ts` assertion + the `resolveRoleBySystemPrompt` test helper (now prefix-matches) updated; `bun run typecheck` and `bun test source/` green (705); a real-LLM run against `llama-server`/"Agents A1" now succeeds (orchestrator→coder→write_file/read_file, ~14k tokens, flow model verified). This is a ~5-line compatibility fix, not a step-13 deliverable; recorded here because it touches the frozen executor. The Ollama endpoint (`qwen3.5:9b`) was unaffected (its template tolerates multiple system messages).

**Design revision (2026-06-26, during step-03 implementation):** operator review redirected the flow view from an ambient static graph (all nodes visible, history-based edges, tier layout) to a **two-component design**: a compact **history top bar** (one small node per role-type and per tool-type that has ever run, cumulative stats, wraps to multiple rows) and a **main area** showing only active + lingering nodes (left-to-right by call depth, current-state-only edges, lingering response legs until the caller acts). Every tool is its own node (not bundled); "backwards always means return" (a call places a new node to the right, the only leftward movement is a response edge). Two further step-03 decisions: (1) the **model derivation moves to the backend** — the frontend is a render-only client of a `FlowModel` (hand-authored on fixture frames in phase A, derived server-side from the full log in step 16), so the client never reconstructs active-path/lingering/in-flight state from a truncated `recentLog` and never invents per-invocation costs the `RunView` doesn't carry; (2) **pathfinding is not wired into the flow view** — main-area edges are straight anchor curves (the active path is a 1–5 node chain), and the pathfinding library stays on disk for the future sequence diagram. The renderer lives in a browser-pure `flow-view.js` (not `render.ts`, which has a runtime import the static server cannot serve). See `plan/ui/PLAN.md` "Flow view (default)" and `plan/ui/03-flow-graph-static-layout.md` for the full design.
- **Step 26** removes the executor's hard cumulative caps (`maxToolCallsPerRole`, `maxTokensPerRole`, `maxRunTimeSeconds`) and the deterministic consecutive-duplicate loop detection, and loosens the tight `2048` per-role generation caps so roles inherit the model's `maxTokens`. Context-window overflow is already handled by the existing endpoint → `context_budget_exceeded` → recovery path; the removed caps were a blunt, redundant guardrail that fired on healthy long-horizon work. Run termination becomes the deployment container's job until step 31 lands the in-band overseer. Accepted gap: no in-band stuck/runaway detection between step 26 and step 31 — ✅ complete (2026-06-25); see `26-budget-cleanup.md` for the closeout (a follow-up review found the entire `RoleDefinition.generation` field was dead config — validated but never read by the LLM caller — so it was removed outright, leaving only model-level sampling parameters; the run-termination note was folded into `docs/architecture.md` "Run termination" rather than recreating the removed `docs/deployment.md`).
- **Step 30** adds the `run_shell` tool — arbitrary shell command execution inside the run workspace. No longer gated on environment isolation (containment comes from the deployment environment), but extreme care should be used when testing against a real LLM since a confused model can wreck the environment.
- **Step 31** is the interrupt & agent-inspection platform, which absorbs the former run-interrupt steps (30–31). It builds two generalized tool families: (1) an agent-callable `trigger_interrupt` and the engine suspension/trigger mechanism that lets a guild-defined agent interrupt running work, and (2) read-only agent-activity inspection tools (`list_role_messages`, `read_message_window`, `search_role_blocks`, `recent_role_tool_calls`) that give a handler bounded, windowed, searchable access to another role's content and reasoning without dumping 256k into its prompt. The first agent on the platform is a **loop-detector** that catches consecutive identical tool calls and LLM-judged reasoning repetition, closing the step-26 stuck-detection gap. The operator/API interrupt (inquiry + plan-modification, formerly steps 30–31) is another trigger source on the same queue — the inquiry/plan-mod halves are handler prompts + engine routing, not separate mechanisms. The platform is the deliverable; the loop detector is the test case. Other interrupt-use agents (on-task checks, post-hoc reviewers) are prompt-only additions on the same tools. Lands the read half of the cross-role compaction primitive; the write half (cross-role `edit_context`) is step 32.
- **Step 32** adds the cross-role context-compaction write half: a context-pressure trigger on the step-31 interrupt platform suspends the active role at the safe point and invokes `context_manager`, which compacts that role's history in place via a cross-role `edit_context` (targeting a registered, suspended role instance), after which the role resumes with the shortened conversation. This makes the `context_manager` role actually useful — today it can only compact its own always-fresh conversation — and removes the step-25 cross-role compaction debt. Lands before the Foundry so the optimizer works against a real compaction mechanism.
- **Step 33** adds run persistence and resumption: the executor checkpoints each role's conversation/budget state at safe points (the drain point step 31 established), and on service restart a run stopped mid-flight (crash, reboot, `docker stop`, Ctrl-C) resumes from its checkpoint instead of being abandoned. Runs that cannot be resumed are marked `interrupted` (a new terminal status) so the UI stops showing them perpetually "in progress". This closes the step-13 signal-handler debt (step 31 delivered the graceful drain; this step adds the checkpoint-on-exit) and makes long runs survive container restarts. Lands after the interrupt platform (31) since the safe-point drain is the checkpoint trigger.
- **Step 34** adds the `researcher` role to the seed Guild — the one role addition the step-29 brainstorm approved. A read-only role (workspace read tools + `fetch_url`) that digests broad, multi-source exploration into compact briefs so the `planner`/`coder` do not fill their context windows with raw material. Guild-only work (prompt + `guild.json` + conformance test), placed last so it is written against the final executor surface; the seed set the Foundry optimizes is then final.
- **Step 35** builds the Foundry — a separate program that consumes the executor as an HTTP client. The design is documented in [`docs/foundry.md`](../docs/foundry.md); the step collaborates with the operator to decide project structure (in-repo subpackage vs separate repository), design the architecture (including per-run environment isolation for benchmark evaluation), and build the full optimization loop end-to-end. Each Foundry benchmark run gets its own container (one container = one benchmark); Foundry parallelism = N containers. The Foundry is the last step: it is built after every other desired feature is done.

The Foundry (step 35) talks to the executor service over HTTP; it never imports `runExecutor` or spawns executor processes directly. Per-run environment isolation (hermetic environments for benchmark evaluation, generalizing the checker-tool commands) is part of the Foundry step. Every original `PLAN.md` phase is accounted for: Phases 1–4 are consolidated in step 00; Phases 5–8 map to the steps above.
