# Step 32 — Context-pressure handoff protocol and cross-role compaction

## Goal

Give the Guild a proactive, quality-preserving answer to context-window pressure, replacing "hit the wall, then cope" as the primary mechanism. The step lands in two independently shippable phases:

- **Phase A — the pressure-handoff protocol.** A real-usage-based pressure trigger fires *while requests still succeed*; the role receives a one-shot append-only notice, writes a handoff brief about its own work, and finishes with a new `context_handoff` error kind; the parent re-spawns a fresh instance of the same role with the brief. Self-written handoff beats third-party pruning for quality, and a fresh small conversation is the KV-cache-cheapest continuation there is.
- **Phase B — the cross-role compaction write half** (the original step-32 scope). A cross-role `edit_context`/`context_info` lets `context_manager` surgically prune a *suspended* role's history using the step-31 inspection tools as its truncated-turn overview. This is the upgrade path for roles where re-delegation is expensive, and a decision point on whether the wall path upgrades from the naive backstop to `context_manager`.

Phase A is the primary deliverable and lands first. Phase B keeps its original design (below) and may be split into a renumbered follow-up at the operator's discretion; the Foundry (step 35) must not start before at least Phase A, so the optimizer works against a real context mechanism.

## Context

Read [`31-interrupt-inspect-platform.md`](31-interrupt-inspect-platform.md) in full — the role-instance registry, the per-run interrupt queue with the safe-point drain, and the Family 2 read-only inspect tools (`list_role_messages` / `read_message_window` / `search_role_blocks` / `recent_role_tool_calls`) are this step's substrate. Read `docs/reference.md` "Context budget exceeded" for the **shipped reactive backstop** (2026-07-26): on an endpoint rejection the executor now compacts in place itself (strip reasoning → drop oldest tool-pairing-safe turns → truncate oversized surviving tool results; estimate calibrated from the endpoint-reported prompt tokens, ~4 chars/token fallback; target 70% of the window), resumes the role with a `[Platform notice — context window exceeded]` user message, logs `context_compacted`, and finishes the role with a `context_budget_exceeded` error card after 3 consecutive rejections or when even the undeletable remainder cannot fit. Also read `source/executor/context-policy.ts` (`compactHistoryForContextBudget`) and the recovery loop in `source/executor/engine.ts`.

That backstop fixed an infinite-retry bug discovered in the same session: the old code appended a synthetic `context_budget_exceeded` *tool* message and retried the same oversized request forever — the model could never see the notice because the request carrying it was itself rejected, and the loop-check platform was blind because its tool-call/token watermarks never advance when no LLM call succeeds. The synthetic message was also an *orphan* tool message (answering no assistant `tool_calls`), a malformed request on strict OpenAI-compatible endpoints — so even a request that did fit would have failed as `llm_unavailable`.

The design review that produced this step's shape (operator, 2026-07-26):

- **Naive heuristic pruning is a last resort, not a mechanism.** Strip-all-reasoning and oldest-first dropping lose information blindly and bust the KV cache from the edit point onward. The backstop stays exactly as-is — by the time it fires, the proactive protocol already gave the model its chance — but nothing in the common path should prune heuristically.
- **The proactive trigger needs no estimator.** Every successful call stores the API-reported `usage.promptTokens` as `roleState.lastPromptTokens`. Pressure checks must use those real numbers; the char estimator stays confined to the post-rejection backstop.
- **The effective context budget is discoverable, not just configurable.** (1) Static math: the real prompt budget is `contextWindow − generation.maxTokens` — llama-server rejects when prompt ≥ n_ctx − n_predict, a 12.5% gap on the seed Guild's 262144/32768 pair. (2) Rejection learning: every `context_budget_exceeded` carrying a reported `promptTokens` is ground truth that the effective budget is *below* that number; track the minimum per run in shared engine state so one role's wall-hit tightens every other role's threshold for the rest of the run. (3) Endpoint probing (llama-server `/props`, Ollama `/api/show`) was considered and **rejected**: incompatible shapes, startup network coupling, and nothing guaranteed on the OpenAI-compatible surface.
- **KV-cache economics rank the options.** Append-only notice ≈ free (prefix cache preserved) < fresh-agent handoff (a new, small conversation) < any mid-history edit (busts from the edit point, naive or intelligent alike). This is why handoff is the primary mechanism and in-place compaction the secondary one.
- **The working agent is the best-qualified summarizer**, and it summarizes best while it still has its full context — hence the pressure notice fires *before* the wall, and the brief is self-written.
- **The "compactor agent with a truncated-turn overview" primitive already exists** as the step-31 read half: `list_role_messages` returns a per-message index/role/size overview of another role's history, `read_message_window` zooms into one message, `search_role_blocks` finds content. Only the write half is missing.

This supersedes the original step-32 text in two places: the reactive path is no longer "finish and re-delegate smaller" (the platform backstop compacts in place first), and the pressure trigger no longer uses "the same estimator the engine's token accounting already trusts" (it uses real reported usage — the engine's token accounting *is* the reported usage).

Two design points were recommended in the review and are recorded here as the working direction; confirm both at step start: (a) introduce a distinct `context_handoff` error kind rather than reusing `context_budget_exceeded` for both paths, so parents route "agent self-summarized, re-spawn with brief" differently from "hit the wall, split smaller"; (b) land Phase A only in this pass, keeping Phase B as the retained second half of this step.

## Deliverables

### Phase A — pressure-handoff protocol

1. **Config.** `executor.contextPressureThreshold` (optional fraction in (0, 1), default `0.8` when unset) in `ExecutorConfig`, `validateExecutorConfig`, and `guild.json`. Always-on by default — the mechanism protects out of the box; the Guild tunes it.
2. **Effective budget.** `effectiveBudget = min(contextWindow − (generation.maxTokens ?? 0), learnedCeiling)` where `learnedCeiling` is the minimum endpoint-reported `promptTokens` over the run's `context_budget_exceeded` rejections (only when reported > 0). The ceiling lives in a shared per-run mutable record on `EngineDependencies` (same precedent as `roleRegistry`/`interruptQueue`), updated in the rejection path of `handleLlmResult`, so every role's threshold tightens after any wall-hit.
3. **Pressure check.** In the `handleLlmResult` success path: `lastPromptTokens ≥ threshold × effectiveBudget` sets a `contextPressureNoticePending` flag on `RoleState` (one-shot per role instance). The notice is appended at the top of the *next* loop iteration — after the turn's tool results, never between an assistant `tool_calls` message and its `tool` results, which is a malformed request on strict endpoints. Log a `context_pressure` event `{ role, promptTokens, effectiveBudget }` and add its `render.ts` formatting.
4. **Notice.** A marked user message `[Platform notice — context pressure]`: you are at N% of the effective context budget; do not start new major work; at the next safe point call `finish` with `status: "error"` and `error.kind: "context_handoff"`, with the summary written as a handoff brief for the fresh agent replacing you — what is done, what remains, key file paths, decisions made, and the immediate next step.
5. **New error kind `context_handoff`.** `types.ts` union, `errors.ts` `ERROR_KINDS`, `guild/tools/finish.json` `error.kind` description, and every consumer of `isErrorKind`. `ResultCard.status` stays `"error"` (control flow treats it as non-success); the kind carries the routing semantics.
6. **Guild prompts.** `coder.md`: the handoff protocol (write the brief; stop starting new work) and how to pick up a task that *contains* a handoff brief. `orchestrator.md`: a child returning `context_handoff` is not a failure — re-delegate a **fresh** instance of the same role with the brief verbatim; do not route to `recovery` and do not split smaller (that is the wall path's response). Its own depth-0 pressure notice means: wrap the run toward a resumable checkpoint — finish in-flight delegations, prefer smaller pieces for what remains, and finish the run with a checkpoint summary the operator can resume from. `recovery.md`: a `context_handoff` row (re-delegate same role fresh with the brief) in case the orchestrator routes one there. The `context_budget_exceeded` wall guidance stays unchanged everywhere.
7. **Tests.** Validation accepts/rejects the threshold; pressure fires when real usage crosses and not below; fires once per role instance (not every turn); the notice lands after the turn's tool results (request wire-order valid); a rejection with reported tokens tightens `effectiveBudget` for later turns; a `context_handoff` card propagates child → parent unchanged; depth-0 notice fires as for any role.
8. **Docs and debt.** `docs/reference.md`: the pressure trigger, effective-budget math and learned ceiling, the handoff protocol, the `context_pressure` event, and the error-table row. Update the "Cross-role context compaction" debt row in [`README.md`](README.md) to describe Phase A as landed (the row itself is removed only by Phase B).

### Phase B — cross-role compaction write half (original step-32 scope, reshaped)

1. **Cross-role `edit_context` and `context_info`.** Both accept an optional `targetRole` (a role-instance id); when present, validated operations apply to the target's `roleState.history` via the registry. The target must be registered (hence suspended — a finished role cannot be compacted) and must not be the caller's own active role; the same operation validation as the self path holds (never touch indices 0/1, ranges in bounds). Absent `targetRole` is byte-for-byte today's behavior. One shared validator, not two.
2. **Guild wiring and prompt rewrite.** `context_manager` gains the Family 2 inspect tools; `guild/prompts/context_manager.md` is rewritten (not patched): it is invoked with a target instance id, inspects the target's history via the overview + windows (never receiving the full history in its own prompt), prunes surgically, confirms the reduction with cross-role `context_info`, and finishes. Preserve always: the target's system prompt, original task, and most recent reasoning and tool results. Update `orchestrator.md`/`recovery.md`'s stale "can only compact its own conversation" claims.
3. **Routing decision (design pass with the operator).** Options: wire a context-pressure trigger on the step-31 interrupt queue (with a re-arm rule so it cannot storm) to `context_manager` for roles where handoff is expensive; and/or route the wall path to `context_manager` (it can run when the target is over the limit — it is a separate role with a fresh small history reading the target through bounded windows) instead of the naive backstop. Either, both, or neither may be chosen; Phase A stands alone.
4. **Tests, docs, debt.** Cross-role edit/info tests (target applies, index 0/1 protection, unknown/unregistered target, self-edit unchanged); handler-flow tests mirroring the loop-detector ones if a trigger is wired; `docs/reference.md` cross-role parameters and any trigger config; **remove** the "Cross-role context compaction" debt row from [`README.md`](README.md).

## Module boundaries

- The proactive trigger reads real reported usage only; the char estimator never leaves the post-rejection backstop.
- Phase A is append-only: no mid-history edits, so no KV-cache loss in the common path.
- The engine provides the channel (pressure detection, notice, error kind, learned ceiling); the handoff *protocol* and compaction *strategy* are Guild prompt work — the Foundry tunes them later.
- Phase B's cross-role primitive lives in the existing built-in tool factory closing over the registry; history mutation stays pure in `context-policy.ts`; any trigger evaluation happens at the single existing drain point — no second interrupt queue, no new safe points.

### Routing decision (operator, 2026-07-26)

The deliverable-3 design pass was taken with the operator: `context_manager` is invoked (a) when the **entry role** crosses the pressure threshold (it has no parent to hand off to), and (b) as the **fallback when a request is rejected for context size** despite the avoidance mechanisms — the naive in-place backstop demotes to last resort (handler absent or failed). Child roles keep the Phase-A handoff as the primary mechanism (KV-cache cheapest).

### What landed (second half)

- **Cross-role `edit_context`/`context_info`.** Both take an optional `targetRole` resolved through the registry: the target must be registered (a finished role is unregistered and cannot be compacted) and must not be the caller (new `BuiltInToolContext.ownRoleId`). Absent `targetRole` is byte-for-byte the old behavior. The compaction guard (`maxCompactionAttempts`) accounts the edited size on the *caller's* list, so the guard still bounds the role doing the compacting.
- **Index 0/1 protection is now code-enforced** in the shared operation validator for both paths (the step's parenthetical assumed it existed; it was prompt-taught only). A batch touching the system prompt or original task rejects atomically; all valid self-edits are unchanged.
- **Engine routing.** `executor.contextHandlerRole` (optional; the seed Guild sets `context_manager`). Depth-0 pressure and context rejections both suspend the role and invoke the handler at the single existing safe point, logged as an `interrupt`/`interrupt_resolved` pair with triggers `context_pressure`/`context_budget_exceeded` and actions `compacted`/`failed` — the flow view roots the handler on a fresh interrupt stack for free. Rejections detected mid-turn park on `RoleState.contextCompactionPending` until the loop top. The naive backstop is extracted unchanged (`applyContextBackstop`) and runs when no handler is configured or the handler fails; depth-0 falls back to the Phase-A handoff notice on handler failure. Re-arm rule: one handler invocation per role instance (the one-shot flag is terminal), so the trigger cannot storm; the wall deferral is separately bounded by the existing 3-rejection cap.
- **Guild.** `context_manager` gains the Family 2 inspection tools and its prompt is rewritten for the cross-role world (inspect via overview + bounded windows, prune with cross-role `edit_context`, confirm with cross-role `context_info`, preserve 0/1 and the most recent turn, never split a tool-call pair, write the finish summary for the target's resume notice). Stale "can only compact its own conversation" claims removed from `orchestrator.md` and `recovery.md`; the orchestrator's depth-0 teaching now expects the compaction interlude (checkpoint wrap demoted to handler-failure fallback). `edit_context.json`'s range description corrected to end-exclusive `[start, end)` — it wrongly said "inclusive" while the code has always been end-exclusive, a direct hazard to a role choosing drop ranges. `validate-data` checks the new wiring.
- **Tests.** Five cross-role tool tests (target applies, 0/1 protection + atomicity, unknown/self target, self path unchanged, guard accounting) and seven engine handler-flow tests (depth-0 interlude, child still gets the notice, no storm, handler-failure fallbacks at both triggers, naive-backstop fallback, rejection-cap bounding).

### Deviations from the plan wording

- **The one-shot is modeled as `contextPressureNotice?: 'pending' | 'sent'`** rather than a `contextPressureNoticePending` boolean plus a guard: the two-state field makes the never-delivered-twice invariant unrepresentable to violate.
- **`finish.json`'s error.kind description had drifted** from `ERROR_KINDS` (it listed the removed `token_budget_exceeded` and lacked step 31's `interrupted`); it now names the full current list including `context_handoff`.
- **The depth-0 checkpoint finish uses `status: "error"` + `context_handoff`** — the plan said "finish the run with a checkpoint summary" without naming status/kind; reusing the same kind keeps one machine-readable signal for "context pressure ended this role or run".
