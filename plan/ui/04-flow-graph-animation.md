# UI step 04 — Flow graph: node lifecycle + merge + edge flow animation

## Goal

Bring the two-component flow view to life with three kinds of animation: (1) **node lifecycle transitions** — entering, shrinking to the top bar, and merging with an existing top-bar slot; (2) **edge flow animation** — marching-ants on active/lingering edges with directionality (forward calls flow left→right, response legs flow right→left); (3) **active node pulse**. All at **turn granularity** (non-streaming). Iterated against the step-01 fixture timelines via the playback harness.

## Context

Read [`PLAN.md`](PLAN.md) ("Flow view (default)" — flow animation, lingering response legs, merge animation), [`03-flow-graph-static-layout.md`](03-flow-graph-static-layout.md) (the two-component `FlowGraph` state: `mainArea` nodes/edges + `topBar` nodes), and `source/web/render.ts` (`LogEvent` types — the events that drive the flow semantics). The turn-level flow mapping, buildable today without executor changes:

- **Agent → agent forward flow:** from `agent_call`/`role_start` (start) until the child's **first `llm_call`** (first turn done). Then a new flow starts from that child toward its tool or child.
- **Agent → tool forward flow:** from `tool_call` (start) to `tool_result` (end).
- **Tool → agent return flow:** on `tool_result`, the response edge flows right→left back to the calling agent.
- **Agent → agent return flow:** on `role_finished` (child returning to parent), the response edge flows right→left back to the parent, and lingers until the parent emits a new action.

Token-level "flow until first byte" is step 15 (deferred, executor-dependent). The playback harness's frame timeline is what makes the animation iterable without a real run — scrubbing frames steps the animation deterministically.

### Node lifecycle transitions

When the `FlowGraph` derivation changes between frames (the playback harness steps frames, or the live poll refreshes), nodes transition between the main area and the top bar:

- **Entering:** a new node appears in the main area at its assigned call-depth position. A brief scale/fade-in.
- **Shrinking to the top bar:** when a node finishes and its caller has acted (the lingering response leg is over), the node animates from its main-area position and size to its type's top-bar slot, shrinking from the full node size to the small top-bar node size.
- **Merging:** if the node's type already has a slot in the top bar, the departing node moves to the existing slot's position and fades out, and the existing slot's counter increments. If no slot exists yet, the node shrinks into a new slot.

The animation is driven by diffing the current frame's `FlowGraph` against the previous frame's: a node present last frame but only in the top bar this frame is a "departing" node; a node in the main area this frame but not last frame is an "entering" node.

### Edge flow animation

Edges in the main area animate based on their kind and the current turn state:

- **`'call'` edges (forward):** marching-ants `stroke-dasharray` animation flowing left→right. Active while the call is in flight (the child hasn't produced its first `llm_call` yet, or the tool result hasn't arrived yet).
- **`'return'` edges (lingering response):** marching-ants flowing right→left. Active while the response leg is visible (the caller hasn't yet acted).
- **`'question'` edges (ask_human):** flowing toward the "You" child node while the question is pending; flowing back to the asking agent after the answer arrives (as a return edge).
- **Static edges:** none in the main area (all main-area edges are active or lingering by definition). The top bar has no edges.

## Deliverables

1. **`source/web/static/flow-graph.js`** — extend `deriveFlowGraph` (or a focused `deriveFlowAnimation(runView, now)` helper) to compute, from the run view's log, the **current animation state**: which edge is `flowing` (and its direction), which is `returning`, which node is `active`/pulsing. Map the turn-level semantics above to the log events; for a completed run, everything is settled (the main area is empty or shows only the root "You", the top bar holds the full history).
2. **`source/web/flow-graph.test.ts`** — cover the animation derivation: an in-progress agent→agent delegation shows the call edge `flowing` until the child's first `llm_call`, then the flow moves to the child's outgoing edge; an in-progress `tool_call` with no `tool_result` yet shows the call edge `flowing`; a `tool_result` triggers the `returning` flow; a completed run has an empty main area and a full top bar. Use the fixture timelines.
3. **`source/web/static/playback.js`** — the `FlowView` passes the animation descriptor to the primitives so edges pick up their `flowing`/`returning` classes and nodes pick up their `active`/`entering`/`departing` classes. Node lifecycle transitions (entering, shrinking to top bar, merging) are driven by diffing consecutive frames' `FlowGraph` states. The playback harness already steps frames; the animation re-derives per frame. No streaming/partial-update plumbing — the whole graph re-renders from the fresh frame (hyperapp diffs the vnodes).

All theme-aware (light/dark tokens from step 02). Respect `prefers-reduced-motion` (disable flow/pulse/transitions, show static active highlight instead).

Deviations from the plan wording, recorded so the next step inherits reality:

- **Animation state is derived from the `FlowModel`, not the run view's log.** The plan's deliverable text reads "compute, from the run view's log, the current animation state," but the model already encodes turn progress in fields the backend derivation will populate: a role node's `costTokens` is set only after its first `llm_call`, a finished node carries a `return` edge back to its caller, and a `question` edge exists only while the ask_human is pending (once answered, the leg becomes a `return` edge). Reading these from the model keeps the renderer self-contained and avoids reconstructing turn state from a truncated `recentLog` window — the client never sees the full log, and the step-03 decision already moved authoritative model derivation to the backend (step 16). The signal generalizes: the real `deriveFlowModel` will populate `costTokens` after the first llm_call too. `deriveFlowAnimation` is therefore `deriveFlowAnimation(model)`, not `deriveFlowAnimation(runView, now)`.
- **Terminal fixture frames were settled to "only the root You."** Step 03's completed/failed/interrupted frames left the returning root role lingering in the main area with a return edge. Step 04's acceptance ("a completed run has an empty main area or only the root You") requires those nodes to have departed to the top bar, and the shrink-to-topbar lifecycle needs a transition to play against. The step-03 shape guards stay green.
- **`tool-call-in-progress` gained a third frame showing `tool_result`.** No step-03 fixture demonstrated a tool returning, so the "tool_result triggers the returning flow" acceptance had no timeline. The new frame 2 adds a `write_file→coder` return edge (lingering) with the `coder→write_file` call settled, exercising the tool return leg.
- **`deriveLifecycle` lives in `flow-view.js`, not `playback.js`.** The plan assigns frame-diffing to the playback harness, but the diff needs the main-area and top-bar pixel coordinate math, which `flow-view.js` owns. Keeping the pure diff in the renderer (and having `playback.js` call it with the two frames' models) keeps the coordinate math single-source and the lifecycle descriptor testable in-memory without a DOM.
- **Departing nodes drift up within the main-area SVG rather than tracking the top-bar slot pixel-for-pixel.** The top bar and main area are independent SVGs that scale to fit their own viewBoxes, so a top-bar slot's screen position does not map cleanly into the main-area coordinate space. The merge-vs-new-slot distinction is a class hook (`flow-node--merging`) on the same motion. With the current top-bar semantics (a slot is added on a type's first invocation, not on departure), every real departure is a merge, so the new-slot branch is exercised only by a synthetic `deriveLifecycle` test; it is kept for faithfulness to the design and for the future where slots might be added lazily.

## Operator review round 2 (2026-06-27)

Operator browser review found five issues, all fixed in-environment (`bun run typecheck` and `bun test source/` re-green):

- **Departing overlay crashed hyperapp and froze the view.** The overlay passed its from/to coordinates as a `style` *string*. Hyperapp v2 iterates `style` as an object (`for (k in style)` → `setProperty` for `-`-prefixed keys); a string iterates as character indices and throws `CSSStyleProperties doesn't have an indexed property setter for '0'`, which aborted the render mid-patch and left the view stuck on the crashing frame (switching scenarios updated the top bar but the main area never re-rendered). Fixed by passing `style` as an object `{ '--from-x': '…px', … }` — hyperapp routes the `-`-prefixed keys through `setProperty` and the CSS keyframe reads them via `var()`. This also unblocked the "no destruction animation" symptom (the crash was preventing the overlay from ever painting) and the "everything breaks if any node is removed" symptom (every terminal frame departs a node, so every terminal frame hit the crash).
- **Return edges overlapped the forward call line.** Returns previously routed source-left → target-right along the same vertical center as the call, painting over it. Returns now route along the **bottom faces** and bow **downward** (a `kind: 'return'` branch in `svg-primitives.js`'s `edgePath`), so the response leg sits below the request line and never overlaps it. `GraphEdge` gained an optional `kind` prop; `flow-view.js` passes `edge.kind` through.
- **`delegation-in-progress` frame 2 was identical to frame 1.** The two frames shared the same FlowModel, so scrubbing to frame 3 showed no change. Frame 2 now advances: the coder has produced its first `llm_call` (`costTokens` set, so `orchestrator→coder` settles to `static`) and is calling `write_file` (a new `coder→write_file` flowing edge), demonstrating "the flow moves to the child's outgoing edge."
- **A child that had moved on to a tool call still showed its incoming delegation edge flowing.** `retry` frame 1's `coder-2`, `deep-multi-role-tree` frame 1's `context_manager`, and `detected-loop` frame 1's `loop_detector` had all called a tool (so their first `llm_call` had landed) but lacked `costTokens`, so `deriveFlowAnimation` kept the incoming call edge `flowing`. Their nodes now carry `costTokens`, so the delegation edge settles to `static` and only the outgoing tool edge flows — matching "the recipient (the current tool) is what's active, not the sender."
- **`pending-question` frame 1 had both `you` and `orchestrator` active.** The recipient of the question edge is the "You" node, so only `you` pulses now; `orchestrator` is the waiting sender and does not.
- **`overflow: hidden` on `.flow-view` clipped strokes and the shrink-up motion.** Removed per operator direction; the SVGs already paint `overflow: visible` and the half-pixel strokes at the viewBox edge (and the departing node drifting to negative y) are no longer cut.

Operator questions answered (no code change):

- **Top-bar nodes turning red/green** is the step-03 terminal-status coloring (`.flow-small-node--success|--error|--interrupted`): a role/tool's history slot strokes green when its last invocation succeeded, red when it errored, dashed when interrupted. As frames advance, a slot gains its terminal status when that invocation finishes. This is pre-existing step-03 behavior, not new to step 04.
- **`prefers-reduced-motion`** is mandated by this step's plan: deliverable 4 ("Respect `prefers-reduced-motion` (disable flow/pulse/transitions, show static active highlight instead)") and the acceptance criterion ("`prefers-reduced-motion` disables flow/pulse/transitions and falls back to a static active highlight"). It is a standard accessibility consideration; kept per the plan. If the operator wants it removed, that is a plan amendment, not an implementation correction.
