# UI step 09 — Sequence diagram view (debug toggle): scaffold + toggle

## Goal

Add the **Sequence** view as a debug toggle alongside the Flow view: an SVG sequence diagram with one column per role plus a "tools" column, messages as horizontal lines on a vertical time axis. This step delivers the scaffold — columns, time axis, message lines, and the toggle — with static rendering against fixtures. Interaction (hover inspector, zoom/pan) is step 10.

## Context

Read [`PLAN.md`](PLAN.md) ("Sequence view (debug toggle)"), [`02-visual-foundation-tokens-svg-primitives.md`](02-visual-foundation-tokens-svg-primitives.md) (the SVG primitives + `viewBox` foundation), and `source/web/render.ts` (`parseLogEvents`, `formatLogEvent`, the full `LogEvent` taxonomy). The sequence diagram is a temporal layout: each event is a horizontal message from its role's column to a target column (a child role for `agent_call`/`role_start`, the tools column for `tool_call`/`tool_result`, the human column for `ask_human`/`human_answer`). The vertical position is the event's timestamp order.

## Deliverables

1. **`source/web/static/sequence-diagram.js`** (new, browser-pure) — `deriveSequenceDiagram(config, runView)`, a pure function producing a `SequenceDiagram`: columns (Human + each role + a tools column, ordered Human → entry → workers → side → tools, with friendly labels), and messages (one per log event, with from-column, to-column, vertical position by timestamp order, and the event's `LogDetailSection`s for step-10 inspection). Pure; covered by `source/web/sequence-diagram.test.ts` against the fixtures. Follows the browser-pure convention established by `flow-graph.js`/`pathfinding.js`/`fixtures.js` (no imports, so the static server can serve it and the test runner can import it from the filesystem).
2. **`source/web/sequence-diagram.test.ts`** — cover `deriveSequenceDiagram`: column set from config; message ordering by timestamp; `agent_call`/`role_start` → child column; `tool_call`/`tool_result` → tools column; `ask_human`/`human_answer` → Human column; completed vs in-progress.
3. **`source/web/static/app.js`** — a `SequenceView` component rendering the columns as vertical lifelines and messages as horizontal lines (with arrowheads for direction), inside an SVG with a `viewBox` sized to the diagram. A **view toggle** (Flow / Sequence) in the run-view header switches the centerpiece; Flow remains the default. Static render this step. Wired into the playback harness so the operator scrubs fixtures in both views.
4. **`source/web/static/styles.css`** — sequence diagram styling: lifelines, message arrows, column headers, theme-aware. The toggle control is clearly a debug affordance (not the product surface).

## Module boundaries

- Web-only, fixture-driven. `sequence-diagram.js` is a new browser-pure derivation; `app.js` gains the view + toggle. No backend or endpoint changes beyond the additive `/sequence-diagram.js` asset route.
- The hover inspector and zoom/pan are deliberately deferred to step 10 so this step stays session-sized (sequence diagrams are fiddly to lay out; isolating the scaffold from the interaction is the right cut).

## Adaptation from the original plan

The plan as written wired the `SequenceView` component and the Flow/Sequence toggle into `app.js`. That proved stale on contact with the rendering pipeline, and the plan was adapted rather than the code forced to match — the same cut step 08 made for the tooltip:

- **Wired into the playback harness (`source/web/static/playback.js`), not `app.js`.** `app.js` renders the legacy panels; the flow view is rendered only by the dev playback harness today, and the live hookup is a later phase-B step (13). The Flow/Sequence toggle, the `SequenceView` centerpiece, and the `view` state therefore live in `playback.js`; `app.js` will receive the identical wiring when step 13 swaps the fixture model for live data. The `deriveSequenceDiagram` / `renderSequenceDiagram` derivation and renderer live in the browser-pure `sequence-diagram.js` module (mirroring `flow-view.js`), so they are exercised in-memory by `sequence-diagram.test.ts`.
- **`renderSequenceDiagram` co-located with `deriveSequenceDiagram` in `sequence-diagram.js`.** The plan's deliverable list named only `deriveSequenceDiagram` for the module; the rendering component was listed under `app.js`. Following the `flow-view.js` convention (where the pure derivation and the `h`-driven renderer share one browser-pure, tested module), the renderer lives in `sequence-diagram.js` too and takes `h` as a parameter so it is exercisable with a fake `h`. The static server's filesystem scan serves the new module with no route change, mirrored by a `GET /sequence-diagram.js` server test.
- **Two arrowhead markers, not one.** A single shared `<marker>` could not be recolored per referencing line, so the renderer declares one arrowhead per direction (`seq-arrow-call` in the accent color, `seq-arrow-return` in the muted edge color) and each message references the marker for its direction.
- **`ask_human`/`human_answer` routing uses a `currentRole` heuristic.** The executor logs these events without a role field (see `source/executor/human-backend.ts`), so the derivation routes them from/to the most recent role-bearing event in the same `recentLog` window, falling back to the Human column when none is in scope. This guarantees the Human column is always an endpoint (the acceptance criterion) and reads correctly against fixtures whose `recentLog` window still carries the asking role; a window truncated to start at the `ask_human` event degrades to a self-marker on Human, which is acceptable for a debug surface.
- **Timeline accumulation across frames.** A single fixture frame's `recentLog` is a 2–3 event sliding window (the flow view needs only current state), so deriving the diagram from the current frame alone collapsed the timeline to the last couple of events. `SequenceView` now reconstructs the full chronological log by accumulating each frame's `recentLog` up to the current frameIndex — the windows overlap contiguously (each is the most-recent N events), so their union, deduplicated by `timestamp|type|summary` and taken in first-seen order, is the full log. First-seen order is chronological because the window only slides forward. When the live backend is wired in (step 13), the live run view's `recentLog` is the full log already, so the accumulation is dropped (it is a fixture-harness concern only).
- **Control-flow builtin tool calls are skipped.** The executor emits a `tool_call`/`tool_result` dispatch wrapper around the `agent`/`finish`/`ask_human` builtins *and* their dedicated semantic events (`agent_call`/`role_start`/`role_finished`, `ask_human`/`human_answer`; see `source/executor/engine.ts` `dispatchAndRecord`). Routing the wrapper to the tools column double-counted the operation and contradicted the flow view's delegation/question edges. `routeMessage` returns `null` for `tool_call`/`tool_result` whose tool is a control-flow builtin, so only the semantic event draws the line. Native tools (`write_file`, `glob_files`, …) still route to the tools column.
- **Role-internal events are dropped (no loopback notches).** An `llm_call` "thinking", an `effort_set`, or a `context_budget_exceeded` is an agent working on its own, not an interaction between participants, so the `default` case of `routeMessage` returns `null` and produces no message. This is what removes the extraneous self-loop "loopback" notches that cluttered the intermediate "the agent received a message but is currently processing" frames: the thinking state is conveyed instead by highlighting the recipient of the last interaction (the agent now processing) via `deriveSequenceActivity`. The diagram now shows only inter-column interactions.
- **A delegated child\'s `role_start` is dropped when its `agent_call` already drew the delegation.** The executor logs `agent_call` (parent delegates) one event before the child\'s `role_start` (child begins), and routing both would draw a *second* arrow on the same parent→child lane — a phantom row appearing on the "child thinking" frame with no corresponding flow-view edge (the flow view shows the delegation as a single edge that appears with the `agent_call` and settles when the child produces its first turn). `deriveSequenceDiagram` tracks the children that already have an `agent_call` row and drops a later `role_start` for the same child, so the delegation is one row and the "child thinking" frame adds no row — the `agent_call` arrow simply loses its flowing highlight (settles to static) and the child node carries the active highlight. The entry role\'s `role_start` (no `agent_call` for it) and a mid-run start whose `agent_call` is outside the visible window (e.g. `retry` frame 0) are kept so the delegation is still represented and the return is not dangling. The `agent_call` already recorded the parent→child link, so `role_finished` still returns to the right column.
- **Self-delegation renders as a loopback.** A self-delegation (`agent_call` where `parent === child`, and the matching self-return `role_finished` returning to the same role) is a real interaction between two invocations of the same role — not a role-internal event — so it produces a message with `from === to`. The renderer draws it as a small rectangular loopback arrow on the role\'s column (right-down-left for calls, left-down-right for returns) instead of a zero-length straight line, with the same highlight rules as cross-column messages: the call loopback flows blue with the node active while in flight, then settles to static with the node still active (the child thinking); the return loopback flows green/red (the outcome) while in flight, then settles to static with the node reverting to active (the parent thinking). For a self-return in flight, the outcome (green/red) takes precedence over the active blue on the single terminal node, since the user wants the result color; no separate source node is rendered (it would overlap the target on the same column). The `parentOf` map is keyed by `(role, depth)` so a self-delegation\'s child entry (`coder|1` → `coder`) does not overwrite the parent\'s entry (`coder|0` → `human`), and the depth-0 `role_finished` still returns to Human. `flowNodeColumn` strips the invocation suffix from the flow node id (`coder-2` → `coder`) so both invocations map to the same column, bridging the flow view\'s per-invocation nodes to the sequence diagram\'s per-type columns.
- **Activity derivation refinements (edge matching, top bar status, hidden-tool caller active, source active when settled).** Four interrelated fixes to `deriveSequenceActivity` keep the sequence view in lockstep with the flow view across scenarios: (1) The line state matches the flow view\'s in-flight edge to the last sequence message **by columns** — a flowing edge to a hidden control-flow tool (e.g. `ask_human`) does NOT animate the last message\'s line, because the hidden tool\'s in-flight state is not the sequence view\'s current operation. (2) The **caller** of a flowing edge to a hidden control-flow tool is treated as active (the sequence view doesn\'t show the tool, so the caller is the one processing) — so when the orchestrator calls `ask_human`, the conductor pulses, not the tools column. (3) Terminal status is scanned from **both the main area and the top bar** — a role that has finished and departed to the top bar still carries its success/error color on its sequence node, so a completed delegation\'s outcome persists. (4) The **source** of the last message can also be active when the line is settled — a thinking role that was the source of the last interaction (e.g. a coder stuck mid-loop after calling `read_file`) pulses on its own column, not on the tool\'s.
- **Overseer agent_calls are filtered at accumulation time.** An overseer role (like a `loop_detector`) may be spawned via an `agent_call` event whose parent→child pair does not appear as a call edge in the flow view (the overseer sits in its own row, not as a child of the caller). Such an agent_call is dropped during the timeline accumulation — checking the flow model of the **frame where the agent_call first appears** (not the current frame), so a past real delegation is kept even after the child departs the main area. `buildCallEdgeColumns` and `isRealDelegation` are exported from `sequence-diagram.js` so the playback harness applies the same filter at accumulation time.
- **`parentOf` bare-key fallback.** The parent-of map records each role\'s caller under both the `(role, depth)` composite key (precise — survives self-delegation) and the bare role-name key (a fallback for `role_finished` events that omit `depth` in the payload, so they can still find the parent — e.g. deep-multi-role-tree\'s `context_manager` returns to `planner`, not Human).
- **Terminal nodes + active/flowing highlight mirroring the flow view.** Each message lands on a small terminal node (an activation marker) on the target column's lifeline, big enough to host a small label and the future hover inspector (step 10). `deriveSequenceActivity(flowModel, flowAnimation, diagram)` mirrors the flow view's current-frame state onto the last (current) message: its line carries the marching-ants animation and accent/return/error color (reusing the flow view's `graph-edge-flow` keyframe and `--svg-*` tokens), and its terminal node — plus, for a return, the source node — carries the active (blue, pulsing)/success (green)/error (red) highlight (reusing the flow view's `graph-node-pulse` keyframe). The flow view's `activeIds`/`edgeStates` are computed by `deriveFlowAnimation` (passed in from `playback.js`, which already imports it, so `sequence-diagram.js` stays import-free) and mapped through `flowNodeColumn` (role invocation ids → role-name columns via `sublabel`, tool nodes → the single `tools` column, `you` nodes → the `human` column). The highlight is CSS-class-only and adds no content surface, so the textContent security invariant is unchanged.
