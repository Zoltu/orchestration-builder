# UI redesign — flow-graph run view

This is a sub-plan for a radical redesign of the web run view, produced by the step-29 brainstorm session. It lives under `plan/ui/` so the main `plan/` sequence stays focused on the executor/Foundry track; the steps here are numbered independently and sequenced among themselves. A short pointer is added to `plan/README.md`; the main plan is not renumbered.

## The problem

The current run view (steps 14–21, 27, 28) is a flat list of debug-oriented panels: role-activity table, raw log rows, config dump. It is a good **development iteration** UI but wrong for the product audience — a **non-developer** left with the page open 24/7. It shows metrics and debugging data, not *what is happening*. A long run looks like an undifferentiated scrolling wall of `planner · llm call` rows.

## The design

Two views, toggled. **Flow** is the default and the product surface; **Sequence** is the debug/investigation surface behind a toggle.

### Flow view (default)

A two-component visualization that separates **current state** from **cumulative history**, so the main area stays calm and legible regardless of how long the run is.

**Top bar (history strip):** a compact strip along the top, wrapping to multiple rows as needed, with one small node per role-type and per tool-type that has ever run this session. Nodes carry cumulative stats (total invocations, total time, total tokens) and a tooltip for extended detail. The strip is unconnected — it is a summary record, not a graph. A finishing node animates from the main area to its type's slot in the top bar; if the slot already exists, the node merges (moves there and fades).

**Main area (active flow):** a left-to-right graph showing only **active and lingering nodes**. Column = call depth in the active call stack. A role can appear multiple times (once per active invocation) — a second `coder` call places a second `coder` node to the right, not a counter on the existing one. Each main-area node shows per-invocation stats (this call's time/tokens, current status), not cumulative totals. The main area holds 1–5 nodes in a typical run, never the whole guild.

- **"Backwards always means return."** A call always places the new node to the right, even if the target role appeared earlier in the path. The only leftward movement is a response edge (a returning node pointing back to its caller).
- **Lingering response legs.** When a node finishes (a child role returns, a tool result arrives), it lingers in the main area with a response edge pointing back to its caller until the caller emits a new action (`llm_call`, `tool_call`, or `role_finished`). Only then does it animate to the top bar. This makes the "tool → builder" response leg visible while the builder hasn't yet acted on the result.
- **Every tool is its own node.** Tools are not bundled into one "Tools" node. Each tool appears as its own node — in the main area only when a call to it is in flight, in the top bar once it has ever been called. A tool node lingers as a response edge (tool → caller) until the caller acts, same as an agent.
- **"You" (Human) node.** A root "You" is always present in the main area at column 1, the root of every call stack, until the task fully finishes (then it animates to the top bar). A child "You" can also appear — like any agent node — when an agent asks a question via `ask_human`. The child "You" lingers as a response edge after the user answers, then animates to the top bar when the caller acts. The top bar has a "You" slot too.
- **Edge routing.** Edges in the main area are straight cubic curves between face anchors: out on the right face, in on the left face for calls (left→right); out on the left, in on the right for returns (right→left). The active path is a 1–5 node chain plus a lingering return leg, so orthogonal no-intersection routing is not needed for the flow view; the pathfinding library (`source/web/static/pathfinding.js`, built and tested in its own step) stays on disk for the future sequence diagram and for cycles/interrupts if the simple layout proves limiting. Flow animation (marching-ants, directionality, active-path glow) is step 04; step 03 delivers the static curves.
- **Multi-row from interrupts.** A user interrupt or loop detector creates a new root at column 1, starting a new row, with edges pointing at the nodes it was inspecting. Parallel children (multiple simultaneously-active children of one node) are anticipated by the design but not implemented now — the executor is sequential. When parallelism lands, each active child gets its own row at the next column.
- **Flow animation along the active path** (step 04). Forward call edges flow left→right; response edges flow right→left. Only the active/lingering edges animate; the top bar is always static. At **turn granularity** (non-streaming, what we ship first): an agent→agent edge flows from `agent_call`/`role_start` until the child's **first `llm_call`**; an agent→tool edge flows from `tool_call` to `tool_result`; the tool→agent return flows on `tool_result`. Node lifecycle animations (entering, shrinking to the top bar, merging) are also step 04. Token-level "flow until first byte" is a future enhancement (step 15) that depends on streaming / a new `llm_call_start` executor event.
- **Human-friendly node labels.** Every role and tool carries a tiered `label` and `description` (`detailed` required; `playful`/`friendly` optional) added to the guild schema (step 12). The UI renders the **`friendly`** tier by default (falling back to `detailed`, then title-cased name) and offers a tier toggle. Guild authors may be playful ("Baking cookies…").
- **"Now" caption.** One plain-language line under the main area derived from the active role/tool — meaning the main area's structure alone can't convey to a non-developer.
- **Costs.** Per-node time + tokens: per-invocation in the main area, cumulative in the top bar; a quiet ambient strip in the page border (elapsed · tokens · effort) always present. Dollar pricing is a trivial later addition if priced.
- **Human question = modal.** `ask_human` opens a **per-run-view modal** (covers the main view, not the page, so a future multi-run world lets the user switch away and back). A child "You" node appears in the main area (like any agent node) showing the question arriving; after the user answers, the child "You" lingers as a response edge back to the asking agent, then animates to the top bar when the caller acts. The root "You" node stays in column 1 throughout. Flash + beep cover the away-from-keyboard case (existing).
- **Result = modal only**, fired on completion, no persistent panel. A clearly-placed **"View result"** CTA button re-opens it. The assistant's final response is rendered as sanitized Markdown (step 27 path).
- **Failure.** Red lines/nodes in the main area's active path; the failing role's top-bar node shows error status. The raw error is surfaced in a copyable block with honest framing ("Something went wrong — here's what the system reported; copy this to share with support or your own assistant"). The machine `kind` is hidden; the `message` is sanitized Markdown. No happy-talk translation.
- **Tooltips.** Hovering/clicking a node or edge (in the main area or the top bar) shows a **friendly-formatted** detail view (labeled blocks, pretty-printed JSON for arguments/results, assistant prose as sanitized Markdown — reusing the `LogDetailSection` shaping from `source/web/render.ts`). A **"copy raw"** button copies the raw JSON for sharing, when visual space allows; the formatted view is for reading.

### Sequence view (debug toggle)

An SVG **sequence diagram**: one column per role plus a "tools" column, messages as horizontal lines on a vertical time axis. Hovering a line shows the request/response; hovering an object at a line's end shows intermediate thinking. Because it is SVG with a `viewBox`, **zoom-to-scroll and pan are nearly free** (tweak the viewBox on wheel/drag); a zoomed-out minimap is deferred until a real need arises. The hover inspector reuses the tooltip/detail components built for the flow view. This view is pragmatic for investigating a completed or stuck run, not for ambient monitoring — it grows long, which is acceptable for a debug surface. "Is it stuck?" investigation lives here, not in the flow view.

### Around the views (unchanged from today)

The left **sidebar** keeps the run list with an obvious "selected" state (one task per row, task on its own line as sanitized Markdown — the step-28 reformat). The **new-run editor** (multiline textarea, Enter=newline, Tab=tab, Ctrl/Cmd+Enter=submit) and **effort slider** stay in the main column above the view. No run label is duplicated on the page — the sidebar selection carries identity.

## Methodology: fixture-first, backend-last

UI work iterates heavily, and iterating against real runs is slow — reproducing a retry, a pending question, an error, or a deep delegation just to see how the UI presents each is wasteful. So this sub-plan is split into two phases:

- **Phase A (steps 01–11): nail the visualization against fixture data.** A rich set of mock run snapshots (as frame sequences, so animation can be iterated) plus a mock config with inline friendly labels is the test bed. From step 03 on, each fixture frame also carries a hand-authored `FlowModel` shaped exactly like the future `/api/runs/:id/flow` endpoint response, so the renderer is iterated against the contract it will eventually consume live. The dev playback harness cycles through a fixture's frames, rendering the model each frame — this is both the iteration surface and the operator review surface. No backend changes in phase A.
- **Phase B (steps 12–16): backend changes + hookup, then retire the legacy UI.** Only after the operator signs off on the visualization do we make the backend changes the nailed-down UI needs: the guild label/description schema (step 12), the server-side `FlowModel` derivation + endpoints (step 16), then wire the renderer to live data (step 13 — a data-source swap, not a rewrite, because phase A rendered the exact contract step 16 produces), and retire the legacy panels (step 14).

This means we never build a backend field the UI turns out not to need, and the heavy visual iteration happens against instant, deterministic, hand-editable fixtures.

## Cross-cutting decisions

- **Light/dark theme follows the browser** via `prefers-color-scheme`. Both palettes must look good; step 02 establishes the token system that supports both.
- **Hand-rolled SVG, no new dependency.** Evaluated d3/dagre/elk/cytoscape — none clear the bar (auditable, no transitive deps, preserves the `textContent` security invariant). The flow graph is constrained enough (1–5 active nodes, call-depth columns) that a custom layout with straight anchor edges suffices; a general-purpose pathfinding library (`source/web/static/pathfinding.js`, built and tested) is kept on disk for the future sequence diagram and as a fallback if manual layout proves limiting for weird guild shapes, but it is not wired into the flow view. Hyperapp renders SVG as vnodes; edges are `<path>`, nodes `<g>`, labels `<text>` (textContent — security invariant holds).
- **SVG structure for maintainability.** Every node is a self-contained component laid out against its own local origin (`0,0`); the layout only assigns each node an `(x, y)` translate. Edges are a separate layer routed by the pathfinding library. No hardcoded padding/margins inside the SVG — borders/padding live on the container. This makes moving a node a one-number change and keeps UI trial-and-error cheap.
- **Security invariant preserved.** Role/tool names, timestamps, counters, and costs are SVG `<text>` textContent. Any agent-authored prose (prompts, responses, summaries, reasoning, error messages, task text) flows only through the step-27 sanitized Markdown pipeline, never `innerHTML`. `docs/security.md` is extended as each step lands.
- **Guild/run mismatch is not handled.** A historical run viewed after a server restart that changed the guild may reference roles the current guild lacks. We write **no code** for this maybe-not-real problem; if it becomes real, it is addressed then.
- **Mobile is out of scope** for this sub-plan. The flow graph and sequence diagram are desktop-first; mobile will need a radically different, separate brainstorm later. Noted for the future.
- **Accessibility is deprioritized** per operator direction. The "now" caption is retained as a product-meaning surface (not an a11y feature), but no special screen-reader work is in scope.

## Module boundaries (whole sub-plan)

- **Phase A is web-only and changes no backend.** The renderer lives in a browser-pure module under `source/web/static/` (`flow-view.js`) — pure, tested in `source/web/flow-view.test.ts` against the fixture `FlowModel`s; the view components, primitives, and dev playback harness live in `source/web/static/`. The browser-pure convention (imports only its sibling `svg-primitives.js`, so the static server can serve the module and the test runner can import it from the filesystem) is why the renderer lives outside `render.ts` (which has a runtime import of `executor/validation.js` the static server does not serve). The `FlowModel` the renderer consumes is hand-authored on fixture frames in phase A; the server-side derivation that produces the same shape from the full log is deferred to step 16 (a phase-B backend step), so the frontend never reconstructs active-path/lingering/in-flight state from a truncated log. Phase A may proceed in parallel with the main plan's executor track (steps 30–32).
- **Phase B touches the backend twice:** step 12 adds the guild label/description schema (`source/executor/types.ts`, `validation.ts`, `loader.ts`, the seed guild, `renderConfig`) — a small, well-contained, data-only change with no runtime behavior change. Step 16 adds the server-side `deriveFlowModel` + `/api/runs/:id/flow` endpoints (the deferred backend half of step 03). Step 13 wires the phase-A renderer to live data (a data-source swap: the fixture `FlowModel` becomes `fetch('/api/run/flow')`). Step 14 retires legacy panels. Step 15 (deferred) is the only executor-runtime change and is gated on the main-plan executor unfreeze (step 30).
- No new runtime dependencies (the SVG work is built-ins + the existing hyperapp + step-27 showdown/highlight.js). New endpoints are added in step 16 (`/api/runs/:id/flow`, `/api/run/flow`); step 12 adds label fields to `/api/config`.
- Every step leaves `bun run typecheck` and `bun test source/` green and the repository clean.

## Operator handoffs

UI work requires human eyes on the rendered result. Every step from 02 onward ends with an **operator browser review** of the fixture-driven view (phase A) or the live view (phase B). The in-environment portion (code, in-memory tests, typecheck) is complete and green before each handoff; the operator confirms the visual/interaction result and the agent iterates the CSS/SVG from feedback until sign-off. Phase A's handoffs use the dev playback harness against fixtures, so no real LLM run is needed to review any scenario — the operator sees retries, pending questions, errors, and deep delegations instantly by selecting a fixture.
