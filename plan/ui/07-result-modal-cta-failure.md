# UI step 07 — Result modal + CTA + failure surfacing

## Goal

On run completion, show the result in a **modal only** (no persistent panel). Provide a clearly-placed **"View result"** CTA button to re-open it after the user closes it. Surface **failure** with red lines/nodes in the main area's active path and error status on the failing role's top-bar node, plus a copyable raw error block with honest framing — no happy-talk translation. Iterated against the success and error fixtures.

## Context

Read [`PLAN.md`](PLAN.md) ("Result = modal only", "Failure"), [`06-human-question-modal-you-node.md`](06-human-question-modal-you-node.md) (the modal pattern this reuses), `source/web/render.ts` (`RunView.result` — the `ResultCard` with status/summary/artifacts; `RunView.error` — the `{ kind, message }`), and `source/executor/types.ts` (`ResultCard`, `ErrorKind`). The run view already carries `result` and `error`; this step presents them as a completion modal + flow-view failure state.

## Deliverables

1. **`source/web/static/app.js`** — a `ResultModal` component fired once when the selected run transitions to a terminal status (`success`/`error`/`needs_clarification`), showing: the result summary (sanitized Markdown), status, and artifacts list (paths as text). On `error`, show the raw error `message` (sanitized Markdown) in a copyable block with honest framing ("Something went wrong — here's what the system reported; copy this to share with support or your own assistant"); hide the machine `kind`. A "copy raw" button copies the full error object as JSON. In the playback harness, the success and error fixtures exercise both paths.
2. **`source/web/static/app.js`** — a **"View result"** CTA button placed where it's easy to find (candidate: the sidebar run row's actions line next to re-run, or the run-summary area header — decide during implementation). Re-opens the `ResultModal` on demand. Quiet after first dismissal but always reachable.
3. **`source/web/static/flow-graph.js`** — extend the flow graph so a failed run colors the active path's edges/nodes red in the main area (`error` state, already supported by the step-02 primitives) and the failing role's top-bar node shows error status. Pure derivation; covered by `flow-graph.test.ts` against the error + retry fixtures.
4. **`source/web/static/styles.css`** — result modal + CTA + error-block styling, theme-aware. Red calibrated for both light and dark (not pure `#ff0000`).
5. **`docs/security.md`** — note the result summary and error message are sanitized Markdown; artifacts are text paths; the error `kind` is intentionally not surfaced to the user.

## Module boundaries

- Web-only, fixture-driven. No backend or endpoint changes. Reuses the modal overlay pattern from step 06.
- The completion modal is non-transient only in the sense that the CTA re-opens it; no dedicated persistent real estate (per `PLAN.md`).

One new browser-pure module:

- `source/web/static/result-modal.js` exports `deriveTerminalResult(runView)` (returns the terminal-status descriptor — summary, artifacts, and on error the message + raw error object — or undefined when the run is not yet terminal) and `ResultModal(h, { descriptor, runLabel, renderMarkdown, onCopyRaw, onClose })`, the overlay vnode builder. `h` and `renderMarkdown` are injected so the component is exercisable in tests with fakes (mirroring `question-modal.js` / `flow-view.js`); the close and copy-raw handlers are supplied by the caller (the harness clears the modal-open flag and writes the JSON to the clipboard; the product client will do the same). The modal is scoped to the run view (an overlay over `.pb-flow`, not a page-wide mask), sharing the question modal's containing block so both stay within the active run.

The top-bar failure surfacing needed a small `flow-view.js` change: `SmallNode` now reads a `status` prop and adds `flow-small-node--error` when `status === 'error'`, re-stroking the box and count in the calibrated error token. This supersedes the step-03 "a slot never turns red or green" stance (the `PLAN.md` "Failure" section requires the failing role's top-bar node to show error status); the prior `flow-view.test.ts` neutrality test was rewritten to assert that success/needs-clarification stay neutral while error turns the slot red, and a new test pins the failed-run fixture's coder slot rendering red with an "errored" hover title. The success path stays neutral so a role that errored mid-run but was retried to success reads as settled, not failed.

Deviations from the plan wording, recorded so the next step inherits reality:

- **The result modal lives in the playback harness (`playback.js`), not `app.js`.** The plan's deliverable 1 names `app.js`, but `app.js` is the product client that does not yet host the flow view (the flow view is wired only into the dev playback harness during phase A; live hookup is step 13). The modal overlays the flow view, which is not in `app.js` yet, so it goes where the flow view is. This is the same call steps 04–06 made; the product modal hookup is step 13/14.
- **The "fires once" semantics are frame-transition-based.** There is no backend to record "already shown for this run" across polls, so the harness derives the fire from the frame-to-frame status change: a frame that newly reaches a terminal status opens the modal, a move back to a non-terminal frame closes it, and a move within the terminal tail preserves the current open state (no re-flash on every render). `computeResultModalOpen(scenarioIndex, oldFrameIndex, newFrameIndex, currentlyOpen)` is pure from `frameIndex` and is wired into every frame-changing action (`Tick`, `Step`, `Scrub`, `TogglePlay`, `SelectScenario`, `SubmitQuestionAnswer`). A scenario switch treats frame 0 as a fresh arrival. The "View result" CTA in the control bar is rendered only on terminal frames and dispatches `OpenResultModal` so the modal is always reachable after dismissal.
- **The error block uses both `runView.error` and `result.error`.** The plan says "the raw error `message`" without naming the source. The descriptor prefers the run-level `error` (`{ kind, message }`) and falls back to the result card's nested `error` (`{ kind, message?, details? }`); the copy-raw button serializes whichever object was chosen. The failed-run fixture carries both with the same kind/message, so both paths exercise the same rendering. The machine `kind` is deliberately never rendered as text — it reaches the DOM only through the copy-raw button's JSON payload (trusted operator clipboard output).
- **`runLabelOf` was extracted and shared with the question modal.** The question modal inlined the run-id-then-task fallback; step 07's result modal needs the same derivation, so it was extracted into a shared `runLabelOf(runView)` helper used by both. No behavior change to the question modal.
- **The "View result" CTA is a standard graph node at column 1 (to the right of the root You), not a big button or an HTML banner.** The plan's deliverable 2 left the CTA's placement open ("placed where it's easy to find"). Two earlier cuts missed: a small `pb-view-result` button buried in the `.pb-controls` strip (operator: "there is no call-to-action button"), and a big 248×88 filled `flow-cta` rect (operator: "should be the same size as a node"). The final design treats the CTA like any other main-area node: it reuses the `GraphNode` primitive (so it is exactly `NODE_WIDTH × NODE_HEIGHT`, laid out at column 1 — the space a terminal run always leaves empty since it settles to only You — and uses the same active/grey styling as a live role node). It is **always present** on a terminal frame, never removed when inactive (unlike a finished role, which departs to the top bar). When active (the result modal is open) it carries `graph-node--active` (blue stroke + pulse) and a flowing You→CTA call edge renders beside it (the same `GraphEdge` 'call'/'flowing' primitives as a real call edge); when inactive (the modal is closed) it is the neutral grey box with no edge. So: click → node stays, turns blue, flow line appears; close modal → flow line disappears, node stays grey. The status (success/error) does not color the CTA — only the label ("View result" / "View error") distinguishes them; active is always blue, inactive always grey, per the operator's spec. `renderFlowView` gained an optional `cta` parameter (`{ label, active, onclick }`); the CTA node + edge are layered over the settled graph after the model nodes, pushed onto the children array only when present so the SVG never carries a null child (the flow-view test's fake `h` does not drop null children). Six tests pin the CTA's presence in both states, its standard-node size/label/onclick, the active-class + flowing-edge pairing, and the inactive no-edge state.
- **The flow-view test's fake `h` does not drop null children** (unlike the question-modal/result-modal fakes, which normalize). `renderFlowView` therefore must never emit a null child — the SVG children array is built conditionally (the CTA is `push`ed only when present) rather than passing a trailing `null` that the real hyperapp would drop but the fake passes through, crashing `allByTag`'s `isVnode(null)` (which returns `true` since `typeof null === 'object'`). This is a test-harness constraint the renderer respects.
- **The copy-raw button wraps its leaf in a state-preserving closure, not a `[leaf, payload]` action pair.** The first implementation wired `onclick: [onCopyRaw, errorToRawJson(error.raw)]` with `onCopyRaw` = the `copyRawError` leaf (`(rawJson) => void`, returns `undefined`). Hyperapp calls an `[fn, payload]` onclick as an action `(state, payload) => state` and uses the return value as the new state — so the leaf received `state` as its `rawJson` (writing the state object to the clipboard as `[object Object]`) and returned `undefined`, corrupting the entire app state (which then broke the close button and every subsequent render). The fix: the component builds `onclick: (state) => { onCopyRaw(rawJson); return state }` — a closure that invokes the injected leaf with the precomputed JSON and returns the state unchanged. The lesson, which generalizes: a leaf that touches an external system (clipboard, network, filesystem) returns `void` and must never be passed bare as a hyperapp action; it must be wrapped by an action that performs the side effect and returns state. The close button was always correct (`onClose` = `CloseResultModal`, a proper state-returning action); it only appeared broken because the copy click had already corrupted state. A regression test asserts the copy handler returns the state it was passed.
