# Task queueing

The operator reports a bug or a task and walks away; the system works through the reported tasks one at a time, autonomously. Every task enters a durable task queue stored at `.orchestration/queue.json`, and a platform scheduler dispatches queued tasks as runs whenever the single run slot is free. There is no interactive mode to fall out of: submitting while the system is idle puts the task at the head of the queue and dispatches it immediately, indistinguishable from today's behavior; submitting while a run is in flight queues the task for its turn. When a run asks a question too early — before any write-capable work has started — the platform parks the task, records the question, and moves on to the next queued task instead of letting one unanswered question block the pipeline. The parked run's checkpoint is kept and frozen at that turn, so the operator's answer re-enters the same run and delivers the answer as the existing `ask_human` tool result rather than starting a new run with a briefing. This document specifies the storage, the scheduler, the parking rule, the answer resume, the legacy briefing, and the HTTP/UI surface. It is a design document: wording and mechanics deliberately left to implementation are listed under "Open implementation details".

## Goals and non-goals

Goals: a user can report several tasks and walk away; the system runs them sequentially without supervision; a task that asks a question before starting work does not stall the pipeline; interim work is visible to later tasks so they do not redo or undo it; the queue survives restarts; the existing single-run contract and API surface keep working unchanged.

Non-goals: parallel execution (runs share one working tree, and serialized execution is correct — see below); an interactive-vs-queued mode toggle (rejected, see "Decisions and rejected alternatives"); automatic retry of failed tasks; git-stash parking of mid-write work; queue management by the LLM; per-task worktrees or branches.

## System context: how runs work today

The service runs strictly one run at a time. `createRunSubmission` (`source/executor/run-submission.ts`) holds a single `activeRunId` slot; a second `submit()` returns `{ ok: false, error: 'run_in_progress' }`, which the HTTP layer maps to 409 (`source/web/request-handler.ts` `handleCreateRun`). Concurrency is structurally impossible: three service-wide singletons — the human backend's run-log binding, the interrupt channel's queue, and the delta channel — are re-bound per run inside `withRunBindings` (`source/serve.ts`). Serialized execution is also correct by design: runs modify the mounted workspace in place, so two concurrent runs would corrupt each other's work.

A run ends in exactly one terminal status — `success`, `error`, `needs_clarification`, or `interrupted` (`source/executor/validation.ts`, `TERMINAL_RUN_STATUSES`). At every terminal status the executor writes the terminal meta and deletes the checkpoint — except `error`, whose checkpoint is kept so the operator can explicitly resume the run with its full context (see "Resume of an errored run" below), and a pre-write park, whose frozen checkpoint is kept so the queue answer can re-enter the same run (see "Parking: the pre-write rule"). A directly-finished `needs_clarification` (no park) has nothing to resume and deletes its checkpoint. Boot reconciliation never auto-resumes an error run (it considers only runs whose meta reads `running`) or a parked run (a checkpoint carrying a parked ask is terminalized and left for the queue answer), so a kept checkpoint makes the run resumable, not resumed. A finished run can be continued as a new run via `continuesFrom`: the API requires the prior meta to be terminal and builds `{ runId, task, summary }` (`source/web/request-handler.ts`, `handleCreateRun`), the executor persists the lineage and injects a briefing into the entry role's initial history only (`source/executor/engine-state.ts`, `EngineContext.continuation`; `source/executor/context/context-builder.ts`, `continuationBriefing`). On boot, `reconcileRunsOnStartup` (`source/executor/startup-reconciliation.ts`) resumes the most recent resumable run through the same single slot, terminalizes a parked run as `needs_clarification` with its checkpoint left in place, and marks every other abandoned run `interrupted`.

`ask_human` (`source/executor/tools/builtin-tools.ts`, `createAskHuman`) blocks with no timeout: the promise settles only when the operator posts to `/api/answer`, and the pending question is in-memory only (`source/executor/human-backend.ts`). A restart-resumed run re-asks from its checkpoint. In the seed Guild only `orchestrator` and `recovery` hold `ask_human`; the `coder` never asks. Project-scoped state that must survive restarts follows the `settings.json` pattern (`source/executor/persistence.ts`, `createReadProjectSettings`/`createWriteProjectSettings`): atomic write-temp + rename, tolerant validated reads through a guard (`isProjectSettings` in `source/executor/validation.ts`), inside the git-excluded `.orchestration/` directory (`source/executor/git-exclude.ts`).

## The queue: storage, item model, state machine

The queue is always-on and universal. Every task enters through it; there is no separate "start now" path, because assuming the user always walks away after submitting makes one code path and one mental model. Submitting while the system is idle enqueues at the head and dispatches immediately, so the user-visible behavior of today's "start now" is preserved exactly. Enqueue-at-tail and head-when-idle coincide because a waiting list can only be non-empty while a run is active — every mutation that creates a waiting item ticks the scheduler — so an idle system's waiting list is provably empty and a tail enqueue is the head; the one exception (a collision retry exhausting its budget, "Dispatch and the scheduler") leaves its item waiting for the next tick, and a start-now request jumping ahead of it is the correct priority anyway.

Storage crosses the module boundary as text through the narrow `QueueStore` port (`read(): string | null`, `write(contents: string)`). The queue module owns JSON parsing, validation through its internal guard, tolerance of a missing or malformed file as an empty queue, and serialization; the write side owns atomic file replacement. The composition root wires the two thin file leaves (`createReadQueueText`/`createWriteQueueText` in `source/executor/persistence.ts`): the reader returns null for a missing or unreadable file, and the writer does write-temp + rename, creating the `.orchestration` directory if needed. The persisted shape never crosses the boundary. The file lives at `.orchestration/queue.json`, already covered by the `.orchestration/` git exclude. Because every mutation is an atomic whole-file write, the queue survives restarts by construction.

An item carries every field a run submission can consume, so the queue knows every run it dispatched:

```json
{
  "id": "…",              // UUID (crypto.randomUUID), the item handle in the API
  "task": "…",            // the operator's task text, verbatim
  "effort": "thorough",   // optional per-item effort override
  "involvement": "collaborative", // optional per-item human-involvement override
  "logLevel": "standard", // optional logging-level override (set by the idle POST /api/runs path; queue-native items resolve through the standard chain)
  "continuesFrom": "run-…", // optional lineage: the run this item's dispatch continues (a parked run awaiting its answer, or a user-initiated Continue)
  "status": "waiting",    // waiting | active | needs_input | done | error | cancelled
  "runId": "run-…",       // set when the scheduler dispatches the item's run
  "queuedAt": "…",        // ISO timestamp
  "settledAt": "…",       // set when the item reaches done/error/cancelled
  "question": "…",        // needs_input: the recorded question
  "answer": "…",          // set when the operator answers
  "resultSummary": "…",   // done/error: the terminal meta's result.summary
  "error": "…",           // error: what the run said went wrong
  "resumeRunId": "run-…",      // internal: the parked run the answer must re-enter (never exposed by the read DTO)
  "resumeToolCallId": "…"      // internal: the ask_human call whose tool result the answer replaces (never exposed)
}
```

The file holds `{ "items": [...] }`, head first; optional fields are omitted when absent, as `RunMeta` does. `resultSummary` is sourced from the terminal meta's `result.summary` — not `summary.txt`, which at settlement time still holds the task-start summary (the completion summary is an async LLM call kicked at the same moment the settlement path runs); when the meta carries no result summary the field is omitted and the UI falls back to the task text, as it does for a missing `summary.txt`. `done`, `error`, and `cancelled` items are kept in the file (with `settledAt`) so the state machine's boot repair and lineage can reference them; pruning is bounded by the queue size policy ("Open implementation details").

State machine (all transitions are whole-file writes):

| From | Event | To |
|---|---|---|
| — | `POST /api/queue`, or idle `POST /api/runs` (head) | `waiting` |
| `waiting` | scheduler tick dispatches | `active` — written without `runId` before `submit` (the dispatching marker), `runId` filled on acceptance |
| `waiting` | `PATCH` edit/reorder, or `DELETE` | edited / `cancelled`; a waiting item bound to a same-run answer resume refuses task/effort/involvement edits (409) but still allows a position-only reorder |
| `needs_input` | `POST /api/queue/:id/answer` | `waiting` (front; `answer` recorded, plus the internal same-run resume pointers when the parked checkpoint still names the question) |
| `waiting` (answer recorded) | scheduler tick dispatches | `active` under the parked run id, then the same-run resume re-enters that run; if the run can no longer be resumed, the pointers are cleared and the legacy briefed dispatch starts a new run |
| `active` | run settles terminal | mapped from the terminal meta: `success` → `done`, `error` → `error`, `needs_clarification` → `needs_input` (`question` recorded; see "Parking: the pre-write rule") |
| `active` (answer recorded) | run settles `needs_clarification` and the frozen checkpoint still names the answered call and question | `waiting` (answer and resume pointers kept) — the answer has not been delivered, so the next tick retries it |
| `active` (answer recorded) | run settles `needs_clarification` after a re-park with a different tool call | `needs_input` with the new question; the delivered answer and resume pointers are dropped |
| `error` | `POST /api/queue/:id/requeue` | `waiting` (tail; ticks the scheduler; `continuesFrom` re-pointed at the errored run) |
| `error` | `POST /api/runs/:id/resume` (the run's own id) | `active` under the same run id — the item re-tracks the live run; its next settlement maps it exactly like any active item's |
| `active` | boot: the item's run meta is already terminal | settled from that meta, exactly the live mapping (crash between the meta write and the settlement write) |
| `active` (with `runId`, answer recorded) | boot: the run meta reads `needs_clarification` and the parked checkpoint still names the answered call and question | `waiting` with the answer intact — the crash landed before the answer was delivered, so the boot tick retries it |
| `active` (no `runId`) | boot: the dispatch crashed mid-window | bound to the boot-resumed run on exact task match, else `waiting` |
| `active` (with `runId`) | boot: the item's run meta still reads `running` (it is the boot-resumed run) | stays `active` untouched — no repair; its own settlement maps it when the resumed run finishes |
| `active` | boot: the item's run reconciled `interrupted` | `waiting` (re-dispatched) |

The last rows are boot-time repairs for the two-files-no-cross-file-atomicity gap: the terminal meta and the queue item are separate files, so a crash between the meta write and the settlement write leaves an `active` item whose run is already terminal — and since `PATCH`/`DELETE`/answer are restricted to other statuses, an unrepaired item would be stuck forever. An answered item is repaired before that mapping: when the run meta reads `needs_clarification` and the frozen checkpoint still names the same tool call and question, the answer never reached the run and the item returns to `waiting` so the boot tick retries it. A re-park with a different tool call, a direct `needs_clarification` whose checkpoint was deleted, or any other terminal means the answer was delivered (or the run finished for another reason), so the normal mapping applies — a missing checkpoint is never read as an undelivered answer. At boot, an `active` item whose run meta reads terminal settles from that meta with exactly the live mapping (`success`/`error` → `done`/`error` with the meta's `result.summary`; `needs_clarification` → `needs_input`, the question recovered from the meta's result summary by the uniform rule "Parking: the pre-write rule" defines). An `active` item with no `runId` is a dispatch cut down mid-window — the tick wrote the dispatching marker, then crashed before filling the id, so the run may or may not have started; unmarked, the resumed run would settle into an item the hook cannot find by `runId` and the task would re-dispatch behind its own duplicate. The repair: the boot tick identifies the resumed run by scanning the run list for the unique `running` meta (`listRunIds` + `readRunMetaById` — reconciliation has already marked every non-resumed run `interrupted` by then, so at most one exists, and no reconciliation-report dependency is added), and the item binds to it when its meta task equals the item's task (sound because only the head is ever mid-dispatch, and identical task texts are interchangeable), returning to `waiting` otherwise for re-dispatch on the boot tick. The fourth case needs no repair: an `active` item with a `runId` whose meta still reads `running` is the boot-resumed run's own item and stays `active` untouched — its settlement maps it when the resumed run finishes. A run reconciled `interrupted` means the service died, not that the task failed, so its item returns to `waiting` and runs again (its `continuesFrom` re-pointed by the same lineage rule "Ordering, answers, and failure semantics" defines); an `active` item whose run directory is unreadable is treated the same way. The settlement mapping only ever touches items whose status is still `active`, which makes park-then-settle and restart-repair order-safe.

## Dispatch and the scheduler

Dispatch is platform code, never the LLM. Queueing is infrastructure like compaction: the orchestrator LLM never sees or manages the queue, no queue tools exist in the Guild, and the Guild is unchanged except for the one prompt addition in "Guild changes: the stale-task fast path". The scheduler owns run creation and is the only caller of submission in the dispatch path.

The scheduler is part of the queue module's single factory `createTaskQueue({ queueStore, readRunMetaById, listRunIds, readRunListSummary, readParkedAskById, resumeParkedRun, submitRun, hasActiveRun, sleep, now })` with no defaults; its `tick` is the orchestration function. The leaves divide by duty: `readRunMetaById` reads one known run's meta, for boot repair and for continuation assembly; `readParkedAskById` reads a run's checkpointed parked ask, so an answer knows which tool call it delivers into and boot repair can tell a delivered answer from an undelivered one; `resumeParkedRun` re-enters that run with the answer; `listRunIds` with `readRunListSummary` (the run-list summary reader, which returns each run's `summary` — null when the summarizer has produced none — alongside its `task` field) enumerate the runs and one-line summaries the briefing assembles, the scheduler itself composing the task-text fallback when a summary is null. One tick: read the queue; if no item is `waiting`, done; otherwise take the head `waiting` item. An answered item carrying the same-run pointers writes an `active` marker with the parked run's id and calls `resumeParkedRun`; an accepted resume returns, `run_in_progress` restores the item to waiting, and `checkpoint_missing`/`not_parked` clears the pointers and falls through to the legacy dispatch below with the question and answer intact. The other path writes the item `active` with no `runId` (the dispatching marker — it closes the crash window between a successful `submitRun` and the queue's `runId` write, per the boot-repair rules above), calls `submitRun(item)`, and fills the `runId` on acceptance. `submitRun` threads the item's fields into the submission layer's `submit` — the task, the `effort`, `involvement`, and `logLevel` overrides, and `continuesFrom` when present, with the continuation's `task`/`summary` read from that prior run's terminal meta via the run-meta reader, exactly the assembly `handleCreateRun` does today — and composes the briefing ("The interim briefing"). Omitting any of these would silently drop lineage or an override for queue-tracked runs, breaking the queue-knows-every-run invariant. On `{ ok: false, error: 'run_in_progress' }` the tick restores the item to `waiting` in the same synchronous cycle (a run is already going — but the dispatching marker was already written, so merely leaving the item as-is would orphan the marker as active-without-id until boot repair); on `{ ok: false, error: 'run_id_collision' }` the tick sleeps past the one-second run-id resolution (`source/executor/run-id.ts` — an immediate retry regenerates the same id, so the retry must wait for the second to roll over) and retries as a fresh read-modify-write cycle that re-reads the queue first, so a mutation landing during the sleep is observed rather than clobbered by a stale write; bounded, leaving the item `waiting` if the retry budget is exhausted (the next tick trigger retries it).

There are three resumption paths and all are explicit. A queue-native resume: when the settlement hook moves an item to `needs_input` it records `continuesFrom` on the item (the parked run), and answering re-enters that same run through the scheduler, delivering the answer as the parked `ask_human` tool result; an item whose checkpoint is gone falls back to a continuation dispatch with the interim briefing. A user-initiated Continue keeps today's `POST /api/runs` contract — it is "start now" semantics: enqueued at the head with the request's `continuesFrom` (and `effort`, `involvement`, and `logLevel`) recorded on the item, dispatched immediately when idle, 409 when busy. And an explicit resume of an error-ended run from its kept checkpoint, `POST /api/runs/:id/resume` ("Resume of an errored run" below) — the operator path that re-enters the same run from an error.

Ticks fire from three places, all cheap and idempotent: (1) run settlement — the submission layer invokes an injected `onRunSettled` callback after the active slot clears on a fulfilled run promise (`source/executor/run-submission.ts` `track`); the callback first maps the settled run's item from the terminal meta (the mapping write precedes the settlement tick it triggers) and then ticks; a rejected run promise never ticks, because it is a fatal service error that tears the service down unchanged ("Ordering, answers, and failure semantics"). (2) Queue mutations that could find the slot free — enqueue, answer, and requeue. (3) Boot — after reconciliation. Concurrency invariant: every queue mutation and scheduler tick is a synchronous whole-file read-modify-write cycle with no await between read and write — per cycle; the collision retry's sleep ends one cycle and the retry begins a fresh one (which re-reads, per above).

Boot order: startup reconciliation first (today's behavior — resume the interrupted run if there is one, mark the rest interrupted; `source/serve.ts`), then exactly one scheduler tick. If a run was resumed, the tick finds the slot busy and no-ops; the resumed run's own settlement ticks the scheduler onward. If nothing was resumed, the tick dispatches the head `waiting` item (after repairing stale `active` items, per the state machine above). Shutdown adds one gate: once the shutdown signal is observed, the wiring flips a flag the settlement tick consults before dispatching, so the tick still maps the settled item but starts no new run. Without the gate, a run finishing inside the 30-second drain would tick the scheduler into dispatching a fresh run that the process then abandons at exit 130 — possible today for zero runs, and pure churn the next boot must repair (reconciliation or re-dispatch); the gate costs one flag and the durable head item simply dispatches on the next boot's tick. A run interrupted mid-flight otherwise reconciles on the next boot exactly as today, with its item repaired by the boot tick.

## Parking: the pre-write rule

v1 has no git-stash parking (deferred — see "Decisions and rejected alternatives"). The rule: when a run calls `ask_human` and no write-capable role has started yet in that run, the platform parks the task instead of blocking. "Write-capable" is generic so future Guilds inherit it: a role whose declared tool set includes a platform-known workspace-mutating tool — `write_file`, `run_shell`, or the checker tools `typecheck`/`test`, which run arbitrary commands — is write-capable. `write_plan` (run bookkeeping, not the project) and `edit_context` (conversations, not the workspace) do not count. The git tools do not count either, deliberately: `git_init`, `git_commit`, and `git_branch` change repository metadata rather than working-tree project content, `git_set_base` changes only the run's base-commit bookkeeping, and the read-only `git_status`/`git_log`/`git_diff`/`git_changes_since_base`/`git_uncommitted_changes` change nothing at all. The run's base commit is recorded at run start (HEAD, or the git empty tree when HEAD is unborn) independently of the park rule — it is bookkeeping, not a workspace write, so it neither sets nor consults the write-capable flag. The engine sets a run-scoped flag when such a role starts (its tool list is known from the Guild at `role_start`); in the seed Guild that is the `coder`, the only writer. The flag is conservative by construction: a false positive (counting a role that never writes) merely degrades a later park to today's blocking behavior, while a false negative would park a run that has already written. The flag rides the checkpoint like `learnedContextCeiling` does (`source/executor/checkpoint.ts`, `RunCheckpoint`), so a restart cannot reset it and park a run whose writes happened before the restart.

Mechanism — platform-initiated termination, with no LLM cooperation required. When the park rule holds, the `ask_human` handler (`source/executor/tools/builtin-tools.ts` `createAskHuman`) does not call the human backend at all — it never registers a pending question — and instead emits the `ask_human` log event itself (so the run's own log stays a faithful record), records `{roleId, toolCallId, question}` in a run-scoped park record (`parkedAsk`), and marks the run to terminate (`parkedQuestion`). Handler frames never park: their checkpoint writes are suppressed, so a parked ask there could never be frozen. The mark is checked at every safe point, which includes between tool dispatches within the current turn as well as the loop top where `drainInterrupts` runs (`source/executor/interrupt-engine.ts`; `source/executor/engine.ts` `executeRoleLoop`); when set, the parked role first writes its checkpoint — now including the live turn's assistant tool-call message and the ask's tool result — then freezes the recorder, and unwinds with a platform-authored `needs_clarification` result card ("waiting for an answer to: <question>"). No further tool dispatch and no further LLM request happen after the mark is set, in the same turn or a later one. The between-dispatch check is load-bearing: a batched `ask_human` + `agent` call in one turn must not start the `coder` after the park decision, or the run writes after the pre-write premise was decided. The unwind mirrors the plan-modification abort pattern (`member.planAbort`, `source/executor/interrupt-engine.ts` `routeOperatorInterrupt`): the mark is run-scoped, so as each child's card propagates up the suspended `agent` calls, every role finishes with the same park card at its next check point; the freeze keeps the first park checkpoint from being overwritten by those later ancestor writes. The run ends in `needs_clarification` with the platform-authored summary in its terminal meta; the small model is never asked to "finish gracefully" and never gets a turn to talk itself out of parking.

The `needs_input` write belongs to the settlement hook, not the park moment. The hook in the submission layer's `track` settlement path sees only the settled `RunMeta` — the run promise carries nothing else, and the engine-scoped park record never crosses to the submission layer (there is no hidden channel) — so it recovers the question by parsing the terminal meta's result summary, uniformly with boot repair. The platform park summary has the exact format `waiting for an answer to: <question>`, and its prefix is stripped to recover the question; a result summary without that prefix is a directly-finished `needs_clarification` — `validateFinishArgs` (`source/executor/tools/builtin-tools.ts`) lets the entry role finish that status with no park, and its summary is LLM-authored — which is stored verbatim as the question. Both parse the same way and the distinction affects only the question text's cleanliness, never behavior.

The answer resume (`source/executor/run-submission.ts` `createResumeParkedRun`, `source/executor/engine.ts` `deliverParkedAnswer`/`continueParkedTurn`): the queue answer reads the frozen checkpoint's `parkedAsk`, records the run id and tool-call id on the item, and the dispatch re-enters the same run under its own id with `queueTracked` restored. On resume the engine finds the last history message with that tool call and replaces only its content with the serialized `{question, answer}` result — the conversation prefix, and therefore the prompt cache, is unchanged — logs `human_answer` with the tool-call id and answer, clears both park marks, unfreezes the recorder, and then continues the parked assistant turn from the call after `ask_human`. A batched turn's remaining calls dispatch exactly as the blocking path would; a later pre-write ask in that turn parks again with a new tool-call id. The unparked checkpoint is written only after the remaining calls have results — at that completed turn boundary, or immediately before a remaining `finish` card returns — because a checkpoint taken mid-batch would have unanswered tool calls. Until that write, the frozen parked checkpoint remains the crash-recovery point: a crash mid-batch either still looks parked, so reconciliation leaves it and the queue's answer-pending rule retries delivery, or a spawned child has already written its own safe-point checkpoint, which serializes the parent's delivered answer and resumes the run normally. A successful answer resume deletes the checkpoint at its terminal status; a re-park keeps the new frozen checkpoint.

Crash-mid-park is safe by the same machinery. A crash before the park checkpoint lands leaves the run `running` with an earlier valid checkpoint, and boot reconciliation resumes it; the queue-tracking mark does not ride the checkpoint, so it blocks on `/api/answer` as any untracked run does (see the accepted degradation below), the question answerable there as always. A crash after the park checkpoint lands leaves a running meta and a checkpoint carrying `parkedAsk`: reconciliation does not auto-resume it. It terminalizes the run as `needs_clarification` with the park summary, leaves the checkpoint on disk, and records the run in `parkedRunIds` (only this crash-parked case appears there; a normally parked run already has a `needs_clarification` meta, which reconciliation skips); the boot queue repair settles the item to `needs_input` (or, when the operator already answered and the crash landed before delivery, releases it to `waiting` so the answer retries). An answer-supplied run that crashes before its post-answer checkpoint write is therefore recovered by the same row: the old parked checkpoint still names the answered call, so the answered item returns to waiting rather than settling to `needs_input` and dropping the answer.

What this does not change: after the first write-capable role has started, `ask_human` behaves exactly as today — blocking until `/api/answer` — because pivoting mid-change would leave incoherent workspace state, and a visible stall beats silent corruption. The read-invalidation hazard this design accepts: a parked task's pre-write reads may be invalidated by the interim tasks that run before its answer arrives. That is acceptable because parking only happens pre-write — nothing but planning state exists to lose — and, on the legacy fallback where a new run is dispatched, the briefing ("The interim briefing") forces re-verification of the premise. One degradation is accepted, and it is the mild one: a run the queue-tracking mark does not cover (a boot-resumed or explicitly error-resumed run — the mark is set by the dispatch path of the process that dispatched the run and does not ride the checkpoint) that asks pre-write blocks exactly as it did before queueing, rather than parking into the void: `ask_human` registers a pending question the operator answers through `/api/answer` as always, so the run stalls visibly and recoverably instead of terminating with a question no endpoint can answer. The question remains visible in the run's history and terminal meta either way.

Foundry impact: pre-write parking changes the human-simulation contract (`docs/foundry.md` "Human simulation"). The simulator answers pending questions as an HTTP client posting to `/api/answer` — but a parked pre-write question never registers a pending entry, so the simulator never sees it: a benchmark run that asks pre-write parks (terminating `needs_clarification` with no workspace change, which fails the benchmark's validation unless the simulator posts to `/api/queue/:id/answer`) instead of pausing for a simulated answer and continuing. The queue answer now resumes the same run, but it is a different endpoint and a queue-item id, not the pending-question id the simulator holds. The `ask_human` log event still fires, so the `humanQuestionPenalty` term still counts the ask; what changes shape is the outcome — `eval.json`'s `humanResponses` can only serve post-write blocking questions through `/api/answer`. `docs/foundry.md` joins the documentation-updates checklist below.

## The interim briefing

A queue-dispatched new run's task text is assembled with a compact briefing, so a task queued hours ago knows what happened meanwhile: when it was queued; one line per run completed since then — enumerated with `listRunIds` and read through the run-list summary reader, each line carrying the full run id so the fast path can cite a real one, `run-<id>: <one-line summary>` (the scheduler composes the task-text fallback when a run's summary is null); queue items cancelled while it waited; and — when the item is a legacy `needs_input` fallback — the recorded question and the operator's answer. The same-run answer resume does not use a briefing: the parked run keeps its own full conversation and receives the answer as a tool result. The briefing ends with a standing instruction that the workspace may have changed since the task was queued. The run ids are not decoration: the fast-path finish format ("Already addressed by run <run id>.") demands one, and a small model asked to produce an id it was never given will hallucinate it.

The briefing reuses the continuation-briefing injection: `RunContinuation` (`source/executor/types.ts`) gains an optional `briefing` field, and `runId` becomes optional (present only when the run genuinely continues a prior run, keeping `meta.continuesFrom` honest — a first queue dispatch records no lineage because there is none). `continuationBriefing` (`source/executor/context/context-builder.ts`) renders the prior-run lines when `runId` is present and the briefing lines when `briefing` is, under the same depth-0 gate and in the same bracketed platform block appended below the task inside the initial user message.

Choosing this over assembling the task text at dispatch: the injection point already exists and is exactly right — depth-0 only, exactly once per run, kept out of `meta.task` (the run list and history view would otherwise render platform bookkeeping as the operator's task), and checkpointed verbatim so a resumed run never re-derives it (the property `source/executor/engine-state.ts` documents for continuations: never set on resume). For the legacy `needs_input` fallback (no frozen parked checkpoint), the scheduler also fills the continuation's `runId`/`task`/`summary` from the parked run's terminal meta (via the run-meta reader), so the fallback run is a genuine continuation of its own earlier attempt.

## Ordering, answers, and failure semantics

Answers: posting an answer to a `needs_input` item records the answer, moves the item to the front of the `waiting` list, and ticks the scheduler. When the parked checkpoint still names the question, the item also records the parked run id and tool-call id, and the dispatch is the same-run resume: the run re-enters its own conversation, the answer replaces the existing `ask_human` tool result, and the conversation prefix is unchanged. When no checkpoint matches (a legacy parked run, or a checkpoint that disappeared), the item clears the resume pointers and dispatches the briefed continuation instead, with the question and answer preserved in the briefing. Lineage follows the re-dispatch: whenever an item will run again, its `continuesFrom` is re-pointed at the just-settled run — a re-park updates it from the original parked run to the attempt that just re-parked, so an answered resume always continues the most recent attempt and never two back, and a requeue after `error` points it at the errored run, so the retry's continuation briefing carries the failure's outcome summary. Answering never preempts the active run — operator plan-modification interrupts remain the only operator-triggered mid-run abort (the park is platform-initiated). Reorder, edit of task/effort/involvement, and removal are allowed for `waiting` items only (a waiting item bound to a same-run answer resume refuses task/effort/involvement edits with 409 but still allows a position-only reorder); a `needs_input` item can only be answered or left. An optional per-item `effort` overrides the project settings effort for that item's run (it rides the existing per-run effort override into `submit`); without it, the standard resolution chain applies (`source/executor/run-submission.ts` `resolveEffort`). An optional per-item `involvement` likewise overrides the project settings involvement for that item's run through the standard chain (`resolveInvolvement`).

Failure semantics: a run ending in `error` marks its item `error` (with the terminal meta's `result.summary` and error), and the settlement tick dispatches the next item — one bad task never stalls the queue; errors surface for triage in the UI. There is no auto-retry in v1: a failed task is a triage decision for the operator, who can retry it from the history list (re-run) or resume it from its checkpoint ("Resume of an errored run" below). The existing fatal-error teardown is distinct and unchanged: a rejected run promise tears the service down non-zero (`source/serve.ts`), leaving the queue durable for the next boot; per-run failure and service failure are different axes.

## Resume of an errored run

An error run keeps its checkpoint (see "System context"), and `POST /api/runs/:id/resume` (`source/executor/run-submission.ts`, `createResumeErroredRun`) is the one explicit, operator-driven path that re-enters it. The briefed continuation stays the fallback for runs with no checkpoint; resuming from a checkpoint is strictly better when one exists because the run keeps its entire conversation instead of redoing all work from a briefing.

Validation gates, in order, each mapping to an HTTP status (`source/web/request-handler.ts`, `handleResumeErroredRun`): no run is currently active (else `409 run_in_progress`, the same single-slot refusal a fresh submission gets); the meta exists (else `404`) and reads exactly `error` (else `409 run_not_errored`); a valid checkpoint exists for the run id (else `409 checkpoint_missing`, whose message points at the briefed-continuation alternative). On success the response is `201 { runId }` — the SAME id as the resumed run: the restored run keeps its own identity, original start time, effort, involvement, and log level, all read from the checkpoint (`source/executor/resume.ts`, `resumeExecutor`), and the resume path re-asserts a `running` meta from them, which replaces the terminal error card in the live meta (the old error card belongs to the log, not the live meta) and flips the run list and run view back to in-progress through the normal file-stat freshness keys (`source/web/snapshot-cache.ts`, `run-list-cache.ts`).

The optional `{ note }` body reaches the resumed conversation as a platform-framed user message — `The operator resumed this run after a failure. Message from the operator: <note>` — appended to the resumed role's restored history at its loop entry (`source/executor/engine-state.ts`, `ResumedRole.resumeNote`): after a suspended turn's tool result has been recorded, so the message ordering stays well-formed on strict endpoints, and before the first LLM request, so the role continuing the work reads the operator's instruction. With no note, nothing is injected — a run that died to `llm_unavailable` has no failed assistant turn to undo, so its history ends cleanly at the last tool result and the agent simply continues. The `run_resumed` log event carries the note as `operatorNote` when present, so the log shows the human intervention on the restart boundary it already marks.

The queue interplay: the item settled to `error` for the resumed run is re-activated under the same run id (`source/executor/queue`, `reactivateErrorItem`) before the resume starts, in the same marker-then-submit order the dispatch path uses — the slot is filled synchronously by the resume, so no scheduler tick can observe the item active against a still-error meta. The settled outcome fields (`settledAt`, `resultSummary`, `error`) are not carried, and the next settlement maps the re-activated item exactly like any active item's. An error run whose item was requeued or cancelled (or never settled into the queue) resumes regardless — the queue record does not gate the run. A resumed run that errors again keeps its checkpoint and stays resumable; the boot rows of the state machine are untouched (an active item whose run meta still reads `running` is left alone, and an item whose run reconciled `interrupted` still re-dispatches).

## Guild changes: the stale-task fast path

The only Guild change is a short "Queued tasks" section in `guild/prompts/orchestrator.md`. A queued task may be stale — work done since it was queued may have fixed or obsoleted it — so before planning, the orchestrator re-verifies the premise cheaply; if an earlier run already addressed the task, it finishes immediately with `status: "success"` and a one-line `Already addressed by run <run id>.` summary, citing an id taken from the briefing (the briefing lines carry the ids precisely for this). That summary convention doubles as UI vocabulary in the history view. The acceptance loop remains the per-item quality gate and bounds the cost of a missed skip: a stale bug that slips past the check passes acceptance trivially (nothing was broken), and the run costs only the check. Draft text (final wording lands when implemented):

```markdown
## Queued tasks

Your task may have waited in a queue while other tasks ran before it, and the workspace may have changed since your task was written — an earlier task may have already fixed the bug or built the feature you were asked for. The briefing below your task lists what ran while it waited, with each run's id; treat it as a hint, not proof.

Before you plan, re-verify the premise of the task cheaply, with one small delegation:

- **A reported bug:** establish the symptom still exists — a `researcher` check of the code involved, or a `coder` delegation that runs a short reproduction command.
- **A requested feature or change:** check the workspace for evidence it already exists.

If an earlier run already addressed the task, call `finish` immediately with `status: "success"` and a one-line summary of the form `Already addressed by run <run id>.` — use a run id from the briefing. Do not plan, do not delegate further work, do not change anything. If the premise holds, continue with the pipeline as usual.
```

## HTTP API

Native queue surface, all under `/api/queue`. Error semantics follow `docs/reference.md`'s HTTP API conventions: a malformed body (non-string task, unknown effort tier, unknown involvement level, non-numeric position, non-string answer) is `400` `{ ok: false, error: 'invalid_body' }`; an unknown item id is `404` `{ ok: false, error: 'not_found' }`; a status-forbidden operation (editing or deleting a non-`waiting` item, answering a non-`needs_input` item) is `409`:

| Endpoint | Behavior |
|---|---|
| `GET /api/queue` | The ordered item list with statuses. |
| `POST /api/queue` | `{ task, effort?, involvement? }` — always enqueues at the tail, never 409; returns `201` with the created item; ticks the scheduler. |
| `PATCH /api/queue/:id` | Edit `task`/`effort`/`involvement` and/or move to a `position` — a 0-based index into the `waiting` list, out-of-range values clamped; `waiting` items only, else 409. A waiting item carrying a pending same-run answer resume refuses field edits with 409 (the resume is bound to its exact task/question); a position-only reorder remains allowed. |
| `DELETE /api/queue/:id` | `waiting` items only — marks the item `cancelled`. |
| `POST /api/queue/:id/answer` | `{ answer }` — `needs_input` items only: records the answer, moves the item to the front of `waiting`, ticks the scheduler. |
| `POST /api/queue/:id/requeue` | `error` items only — returns the item to `waiting` at the tail (the endpoint remains for programmatic clients; the UI no longer exposes a one-click re-queue); ticks the scheduler — the common single-item case is a requeue while idle, and without the tick it would sit `waiting` forever — and re-points the item's `continuesFrom` at the errored run. |

`POST /api/runs` keeps today's external contract exactly (`docs/reference.md` "HTTP API"): when idle it dispatches immediately and returns 201 `{ runId }`; when a run is in flight it returns 409 `{ ok: false, error: 'run_in_progress' }` and enqueues nothing — scripts depend on that behavior. Internally, though, it now enqueues an item at the head — recording the request's `continuesFrom` and `logLevel` on the item — and lets the scheduler dispatch it within the same request, so every active run is queue-tracked (a run the queue does not know could never be parked, continued, or settled into the queue). A same-second `run_id_collision` that survives the tick's bounded retry surfaces as today's 409 `{ ok: false, error: 'run_id_collision' }`, and the just-created head item is removed so the caller's resubmit behaves exactly as it does today. `POST /api/answer` and `GET /api/questions` keep working unchanged for blocking (post-write) questions of the active run; parked questions are answered through `POST /api/queue/:id/answer` instead — the park path never registers a pending question in the human backend.

`GET /api/run` (the singular active-run view, `handleActiveRun` in `source/web/request-handler.ts`) keeps working with "active" meaning the active item's run — the most recently dispatched one; the head of the queue can be a `needs_input` item while a later item's run is in flight, so "head" is the wrong anchor. When nothing is running it keeps today's `lastRunId()` most-recent-run fallback so the watch screen is unchanged.

## UI interaction model

Queueing and history are one screen, the History tab (the separate Queue tab is gone; `source/web/static/ts/app.ts`): its list shows the queued items at the top in order — `waiting` (drag to reorder, plus Edit and Remove), `active` (read-only, labeled "running"), and `needs_input` (with an inline answer box) — then the run history below; finished queue items (`done`/`error`/`cancelled`) are no longer listed in the queued part, and a finished task appears as a run in the history list below. A small badge on the History tab shows the pending-queue count when it is greater than zero. The client no longer offers a one-click re-queue: a failed task is retried from the history list (re-run) or resumed from its checkpoint, while the `POST /api/queue/:id/requeue` endpoint remains for programmatic clients. Queued rows collapse with the same expand-button pattern as history rows, not native `<details>`. The compose box becomes "Add task" and — with the queue universal — stops being disabled while a run is active (today's guard at `composeDisabled`, `source/web/static/ts/app.ts`). The merged screen's rendering is pinned to the same invariant as every other operator content (`docs/security.md` "Web client rendering pipeline"): untrusted strings — task text, questions, answers, result summaries — render through the sanitized-Markdown/`textContent` split, never as raw markup. The watch screen is unchanged, and the "already addressed by run <id>" summary convention appears naturally in the history list. UI details beyond this interaction model are implementation's business.

## Module and test mapping

Per `AGENTS.md` ("Architecture"), every piece lands in its tier:

- **Queue module** — `source/executor/queue/` with `index.ts` as the only public entrypoint: the read-only `QueueItemView`/`QueueView` DTOs, the queue factory `createTaskQueue`, the `QueueStore` text port, and the HTTP-facing result types. The persisted item shape, its guards, serialization, and the pure state machine stay private. Every `read` and every mutator returns freshly cloned DTOs, so a caller cannot mutate module-owned state, and the public operations document their preconditions, state transitions, and typed failure reasons in the entrypoint contract. Consumers call the factory's `read`, `enqueue`, `submitNow`, `patch`, `cancel`, `answer`, `requeue`, `reactivateErrorItem`, `tick`, `onRunSettled`, and `observeShutdown` operations rather than reading, mutating, and writing the queue themselves. The module never imports the submission layer; dispatch receives a `submitRun` port. Fully in-memory testable: text stores, fixed clocks, no filesystem.
- **Persistence leaves** — `createReadQueueText`/`createWriteQueueText` in `source/executor/persistence.ts`, on the `createReadProjectSettings`/`createWriteProjectSettings` pattern. The queue module consumes them through `QueueStore`, so the leaves carry text only. Not unit-tested (thin filesystem wrappers, like the settings leaves).
- **Scheduler** — the module's `tick` (and the settlement hook `onRunSettled`) takes `queueStore, readRunMetaById, listRunIds, readRunListSummary, readParkedAskById, resumeParkedRun, submitRun, hasActiveRun, sleep, now`, no defaults; `readRunMetaById` is the run-meta reader leaf (boot repair of phantom `active` items and continuation assembly from the parked run's meta), `readParkedAskById` reads the frozen checkpoint's parked ask, `resumeParkedRun` re-enters that run with the answer, and `listRunIds` with `readRunListSummary` are the run-enumeration leaves the briefing assembles from (completed runs since `queuedAt`; the reader returns each run's `summary` — null when none — alongside its `task` field, and the scheduler composes the task-text fallback itself). Tested with a fake `submitRun` (recording calls, returning scripted results), a text queue store, fake run-meta/run-list/parked-ask readers, a scripted `resumeParkedRun`, and a fake `sleep`/`now`: dispatch-on-idle, no-op-when-busy, dispatch-marker written before `submit` and restored to `waiting` on `run_in_progress`, bound-or-released at boot (with the resumed `running`-meta scan), the with-`runId` resumed item left untouched, collision retry re-reads after the fake sleep, park ordering, answer-front dispatch with `continuesFrom` threading, same-run answer dispatch (marker, resume payload, no `submitRun`), `run_in_progress` restore, checkpoint_missing/not_parked fallback, answered-item release on a same-call settlement and boot repair, re-park-with-new-call settlement, lineage re-pointing on requeue and re-park, DTO projection hiding the internal resume pointers, `logLevel`/`effort`/`involvement` threading, error mapping, boot repair from a terminal meta, interrupted-to-waiting re-dispatch, and the shutdown gate suppressing dispatch while still mapping the settled item.
- **Settlement hook** — `createRunSubmission` gains a required `onRunSettled` dependency invoked from `track`'s fulfillment branch; `source/executor/run-submission.test.ts` covers that it fires exactly once per settled run and never on the rejection branch.
- **Park mechanism** — the run-scoped write-capability tracker, `parkedAsk`/`parkedQuestion`, and the freeze inside the executor's ask-handler path, checked at the loop top and between tool dispatches (`source/executor/tools/builtin-tools.ts`, `source/executor/engine.ts` `dispatchToolCallSequence`/`executeRoleLoop`, checkpointed via `source/executor/checkpoint.ts`); `source/executor/engine.test.ts` exercises park-vs-block through fake handlers and a fake `humanBackend`, in memory — including a batched `ask_human` + `agent` turn where the park mark must prevent the `coder` from starting, and the answer resume's in-place tool-result replacement, `human_answer` log, park-state clearing, batched remaining-call dispatch, mismatch failure, and re-park.
- **Answer resume** — `createReadParkedAskById`/`createResumeParkedRun` in `source/executor/run-submission.ts`, the executor's checkpoint keep/delete rule and `deliverParkedAnswer`/`continueParkedTurn`, and startup reconciliation's parked-run terminalization (`parkedRunIds`); covered by `run-submission.test.ts`, `executor.test.ts`, and `startup-reconciliation.test.ts` in memory.
- **Briefing injection** — the `RunContinuation` extension in `source/executor/types.ts` and rendering in `source/executor/context/context-builder.ts`; `source/executor/context/context-builder.test.ts` covers the block's placement and the depth-0 gate.
- **Endpoints** — the `/api/queue` routes in `source/web/request-handler.ts`, with the queue module in `RequestHandlerConfig`; handler tests inject an in-memory queue module exactly as the existing route tests do.

## Decisions and rejected alternatives

- **Always-on universal queue** (D1) — one code path, one mental model; the operator's rule is "assume the user always walks away after submitting". *Rejected:* an interactive-vs-queued mode toggle — queue membership is universal; a toggle would fork every path (submit, park, briefing, UI) for behavior the queue already makes identical.
- **Git-stash parking** — deferred, not rejected forever. v1 parks only pre-write, where there is nothing to stash, so the platform-initiated termination suffices; revisit only if mid-work questions prove common enough that blocking on them is a real cost. Mid-write parking would need workspace capture/restore (stash or snapshot) with all its coherence hazards.
- **Per-task worktrees/branches** — rejected: the workspace-model change is large (every tool, the in-place contract, and the foundry's assumptions assume one tree), and only multi-agent parallelism would want it — which is not a goal.
- **Timeout-then-park** — rejected: N is unknowable (a planning question may legitimately take minutes of thought), and an arbitrary timeout either fires on healthy runs or never fires; a run that silently parked itself after an arbitrary wait erodes trust. Parking is keyed to a structural fact (pre-write), not a guess.
- **Queue-time duplicate detection by text similarity** — rejected: the stale-task fast path ("Guild changes: the stale-task fast path") checks the premise against the real workspace at run time, which is strictly better than fuzzy text matching at enqueue time; similarity search also cannot tell "same bug" from "same words".
- **LLM queue-management tools** — rejected: the platform does bookkeeping perfectly and for free; queue tools would spend tokens and trust on work that is infrastructure. The Guild stays unchanged except for the prompt in "Guild changes: the stale-task fast path".
