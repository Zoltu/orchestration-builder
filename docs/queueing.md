# Task queueing

The operator reports a bug or a task and walks away; the system works through the reported tasks one at a time, autonomously. Every task enters a durable task queue stored at `.orchestration/queue.json`, and a platform scheduler dispatches queued tasks as runs whenever the single run slot is free. There is no interactive mode to fall out of: submitting while the system is idle puts the task at the head of the queue and dispatches it immediately, indistinguishable from today's behavior; submitting while a run is in flight queues the task for its turn. When a run asks a question too early — before any write-capable work has started — the platform parks the task, records the question, and moves on to the next queued task instead of letting one unanswered question block the pipeline. This document specifies the storage, the scheduler, the parking rule, the briefing a queued task receives about what happened while it waited, and the HTTP/UI surface. It is a design document: wording and mechanics deliberately left to implementation are listed under "Open implementation details".

## Goals and non-goals

Goals: a user can report several tasks and walk away; the system runs them sequentially without supervision; a task that asks a question before starting work does not stall the pipeline; interim work is visible to later tasks so they do not redo or undo it; the queue survives restarts; the existing single-run contract and API surface keep working unchanged.

Non-goals: parallel execution (runs share one working tree, and serialized execution is correct — see below); an interactive-vs-queued mode toggle (rejected, see "Decisions and rejected alternatives"); automatic retry of failed tasks; git-stash parking of mid-write work; queue management by the LLM; per-task worktrees or branches.

## System context: how runs work today

The service runs strictly one run at a time. `createRunSubmission` (`source/executor/run-submission.ts`) holds a single `activeRunId` slot; a second `submit()` returns `{ ok: false, error: 'run_in_progress' }`, which the HTTP layer maps to 409 (`source/web/request-handler.ts` `handleCreateRun`). Concurrency is structurally impossible: three service-wide singletons — the human backend's run-log binding, the interrupt channel's queue, and the delta channel — are re-bound per run inside `withRunBindings` (`source/serve.ts`). Serialized execution is also correct by design: runs modify the mounted workspace in place, so two concurrent runs would corrupt each other's work.

A run ends in exactly one terminal status — `success`, `error`, `needs_clarification`, or `interrupted` (`source/executor/validation.ts`, `TERMINAL_RUN_STATUSES`). At every terminal status the executor writes the terminal meta and deletes the checkpoint (`source/executor/executor.ts`, `runExecutor`/`resumeExecutor`). A finished run can be continued as a new run via `continuesFrom`: the API requires the prior meta to be terminal and builds `{ runId, task, summary }` (`source/web/request-handler.ts`, `handleCreateRun`), the executor persists the lineage and injects a briefing into the entry role's initial history only (`source/executor/engine-state.ts`, `EngineContext.continuation`; `source/executor/context-builder.ts`, `continuationBriefing`). On boot, `reconcileRunsOnStartup` (`source/executor/startup-reconciliation.ts`) resumes the most recent resumable run through the same single slot and marks every other abandoned run `interrupted`.

`ask_human` (`source/executor/builtin-tools.ts`, `createAskHuman`) blocks with no timeout: the promise settles only when the operator posts to `/api/answer`, and the pending question is in-memory only (`source/executor/human-backend.ts`). A restart-resumed run re-asks from its checkpoint. In the seed Guild only `orchestrator` and `recovery` hold `ask_human`; the `coder` never asks. Project-scoped state that must survive restarts follows the `settings.json` pattern (`source/executor/persistence.ts`, `createReadProjectSettings`/`createWriteProjectSettings`): atomic write-temp + rename, tolerant validated reads through a guard (`isProjectSettings` in `source/executor/validation.ts`), inside the git-excluded `.orchestration/` directory (`source/executor/git-exclude.ts`).

## The queue: storage, item model, state machine

The queue is always-on and universal. Every task enters through it; there is no separate "start now" path, because assuming the user always walks away after submitting makes one code path and one mental model. Submitting while the system is idle enqueues at the head and dispatches immediately, so the user-visible behavior of today's "start now" is preserved exactly. Enqueue-at-tail and head-when-idle coincide because a waiting list can only be non-empty while a run is active — every mutation that creates a waiting item ticks the scheduler — so an idle system's waiting list is provably empty and a tail enqueue is the head; the one exception (a collision retry exhausting its budget, "Dispatch and the scheduler") leaves its item waiting for the next tick, and a start-now request jumping ahead of it is the correct priority anyway.

Storage follows the `settings.json` pattern exactly (`source/executor/persistence.ts` "settings"): `createReadQueue` tolerates a missing or malformed file as an empty queue and validates every read through a guard (`isTaskQueue`, in the style of `isProjectSettings`); `createWriteQueue` writes atomically (write-temp + rename, creating the `.orchestration` directory if needed). The file lives at `.orchestration/queue.json`, already covered by the `.orchestration/` git exclude. Because every mutation is an atomic whole-file write, the queue survives restarts by construction.

An item carries every field a run submission can consume, so the queue knows every run it dispatched:

```json
{
  "id": "…",              // UUID (crypto.randomUUID), the item handle in the API
  "task": "…",            // the operator's task text, verbatim
  "effort": "thorough",   // optional per-item effort override
  "logLevel": "standard", // optional logging-level override (set by the idle POST /api/runs path; queue-native items resolve through the standard chain)
  "continuesFrom": "run-…", // optional lineage: the run this item's dispatch continues (a parked run awaiting its answer, or a user-initiated Continue)
  "status": "waiting",    // waiting | active | needs_input | done | error | cancelled
  "runId": "run-…",       // set when the scheduler dispatches the item's run
  "queuedAt": "…",        // ISO timestamp
  "settledAt": "…",       // set when the item reaches done/error/cancelled
  "question": "…",        // needs_input: the recorded question
  "answer": "…",          // set when the operator answers
  "resultSummary": "…",   // done/error: the terminal meta's result.summary
  "error": "…"            // error: what the run said went wrong
}
```

The file holds `{ "items": [...] }`, head first; optional fields are omitted when absent, as `RunMeta` does. `resultSummary` is sourced from the terminal meta's `result.summary` — not `summary.txt`, which at settlement time still holds the task-start summary (the completion summary is an async LLM call kicked at the same moment the settlement path runs); when the meta carries no result summary the field is omitted and the UI falls back to the task text, as it does for a missing `summary.txt`. `done`, `error`, and `cancelled` items are kept in the file (with `settledAt`) so the UI can show recent outcomes; pruning is bounded by the queue size policy ("Open implementation details").

State machine (all transitions are whole-file writes):

| From | Event | To |
|---|---|---|
| — | `POST /api/queue`, or idle `POST /api/runs` (head) | `waiting` |
| `waiting` | scheduler tick dispatches | `active` — written without `runId` before `submit` (the dispatching marker), `runId` filled on acceptance |
| `waiting` | `PATCH` edit/reorder, or `DELETE` | edited / `cancelled` |
| `needs_input` | `POST /api/queue/:id/answer` | `waiting` (front; `answer` recorded) |
| `active` | run settles terminal | mapped from the terminal meta: `success` → `done`, `error` → `error`, `needs_clarification` → `needs_input` (`question` recorded; see "Parking: the pre-write rule") |
| `error` | `POST /api/queue/:id/requeue` | `waiting` (tail; ticks the scheduler; `continuesFrom` re-pointed at the errored run) |
| `active` | boot: the item's run meta is already terminal | settled from that meta, exactly the live mapping (crash between the meta write and the settlement write) |
| `active` (no `runId`) | boot: the dispatch crashed mid-window | bound to the boot-resumed run on exact task match, else `waiting` |
| `active` (with `runId`) | boot: the item's run meta still reads `running` (it is the boot-resumed run) | stays `active` untouched — no repair; its own settlement maps it when the resumed run finishes |
| `active` | boot: the item's run reconciled `interrupted` | `waiting` (re-dispatched) |

The last rows are boot-time repairs for the two-files-no-cross-file-atomicity gap: the terminal meta and the queue item are separate files, so a crash between the meta write and the settlement write leaves an `active` item whose run is already terminal — and since `PATCH`/`DELETE`/answer are restricted to other statuses, an unrepaired item would be stuck forever. At boot, an `active` item whose run meta reads terminal settles from that meta with exactly the live mapping (`success`/`error` → `done`/`error` with the meta's `result.summary`; `needs_clarification` → `needs_input`, the question recovered from the meta's result summary by the uniform rule "Parking: the pre-write rule" defines). An `active` item with no `runId` is a dispatch cut down mid-window — the tick wrote the dispatching marker, then crashed before filling the id, so the run may or may not have started; unmarked, the resumed run would settle into an item the hook cannot find by `runId` and the task would re-dispatch behind its own duplicate. The repair: the boot tick identifies the resumed run by scanning the run list for the unique `running` meta (`listRunIds` + `readRunMetaById` — reconciliation has already marked every non-resumed run `interrupted` by then, so at most one exists, and no reconciliation-report dependency is added), and the item binds to it when its meta task equals the item's task (sound because only the head is ever mid-dispatch, and identical task texts are interchangeable), returning to `waiting` otherwise for re-dispatch on the boot tick. The fourth case needs no repair: an `active` item with a `runId` whose meta still reads `running` is the boot-resumed run's own item and stays `active` untouched — its settlement maps it when the resumed run finishes. A run reconciled `interrupted` means the service died, not that the task failed, so its item returns to `waiting` and runs again (its `continuesFrom` re-pointed by the same lineage rule "Ordering, answers, and failure semantics" defines); an `active` item whose run directory is unreadable is treated the same way. The settlement mapping only ever touches items whose status is still `active`, which makes park-then-settle and restart-repair order-safe.

## Dispatch and the scheduler

Dispatch is platform code, never the LLM. Queueing is infrastructure like compaction: the orchestrator LLM never sees or manages the queue, no queue tools exist in the Guild, and the Guild is unchanged except for the one prompt addition in "Guild changes: the stale-task fast path". The scheduler owns run creation and is the only caller of submission in the dispatch path.

The scheduler is an orchestration function `createTaskScheduler({ readQueue, writeQueue, readRunMetaById, listRunIds, readRunListSummary, submitRun, sleep, now })` with no defaults. The leaves divide by duty: `readRunMetaById` reads one known run's meta, for boot repair and for continuation assembly; `listRunIds` with `readRunListSummary` (the run-list summary reader, which returns each run's `summary` — null when the summarizer has produced none — alongside its `task` field) enumerate the runs and one-line summaries the briefing assembles, the scheduler itself composing the task-text fallback when a summary is null. One tick: read the queue; if no item is `waiting`, done; otherwise take the head `waiting` item, write it `active` with no `runId` (the dispatching marker — it closes the crash window between a successful `submitRun` and the queue's `runId` write, per the boot-repair rules above), call `submitRun(item)`, and fill the `runId` on acceptance. `submitRun` threads the item's fields into the submission layer's `submit` — the task, the `effort` and `logLevel` overrides, and `continuesFrom` when present, with the continuation's `task`/`summary` read from that prior run's terminal meta via the run-meta reader, exactly the assembly `handleCreateRun` does today — and composes the briefing ("The interim briefing"). Omitting any of these would silently drop lineage or the log-level override for queue-tracked runs, breaking the queue-knows-every-run invariant. On `{ ok: false, error: 'run_in_progress' }` the tick restores the item to `waiting` in the same synchronous cycle (a run is already going — but the dispatching marker was already written, so merely leaving the item as-is would orphan the marker as active-without-id until boot repair); on `{ ok: false, error: 'run_id_collision' }` the tick sleeps past the one-second run-id resolution (`source/executor/run-id.ts` — an immediate retry regenerates the same id, so the retry must wait for the second to roll over) and retries as a fresh read-modify-write cycle that re-reads the queue first, so a mutation landing during the sleep is observed rather than clobbered by a stale write; bounded, leaving the item `waiting` if the retry budget is exhausted (the next tick trigger retries it).

There are two resumption paths and both are explicit. A queue-native resume: when the settlement hook moves an item to `needs_input` it records `continuesFrom` on the item (the parked run), and answering dispatches through the scheduler as a continuation of that run. A user-initiated Continue keeps today's `POST /api/runs` contract — it is "start now" semantics: enqueued at the head with the request's `continuesFrom` (and `logLevel`) recorded on the item, dispatched immediately when idle, 409 when busy.

Ticks fire from three places, all cheap and idempotent: (1) run settlement — the submission layer invokes an injected `onRunSettled` callback after the active slot clears on a fulfilled run promise (`source/executor/run-submission.ts` `track`); the callback first maps the settled run's item from the terminal meta (the mapping write precedes the settlement tick it triggers) and then ticks; a rejected run promise never ticks, because it is a fatal service error that tears the service down unchanged ("Ordering, answers, and failure semantics"). (2) Queue mutations that could find the slot free — enqueue, answer, and requeue. (3) Boot — after reconciliation. Concurrency invariant: every queue mutation and scheduler tick is a synchronous whole-file read-modify-write cycle with no await between read and write — per cycle; the collision retry's sleep ends one cycle and the retry begins a fresh one (which re-reads, per above).

Boot order: startup reconciliation first (today's behavior — resume the interrupted run if there is one, mark the rest interrupted; `source/serve.ts`), then exactly one scheduler tick. If a run was resumed, the tick finds the slot busy and no-ops; the resumed run's own settlement ticks the scheduler onward. If nothing was resumed, the tick dispatches the head `waiting` item (after repairing stale `active` items, per the state machine above). Shutdown adds one gate: once the shutdown signal is observed, the wiring flips a flag the settlement tick consults before dispatching, so the tick still maps the settled item but starts no new run. Without the gate, a run finishing inside the 30-second drain would tick the scheduler into dispatching a fresh run that the process then abandons at exit 130 — possible today for zero runs, and pure churn the next boot must repair (reconciliation or re-dispatch); the gate costs one flag and the durable head item simply dispatches on the next boot's tick. A run interrupted mid-flight otherwise reconciles on the next boot exactly as today, with its item repaired by the boot tick.

## Parking: the pre-write rule

v1 has no git-stash parking (deferred — see "Decisions and rejected alternatives"). The rule: when a run calls `ask_human` and no write-capable role has started yet in that run, the platform parks the task instead of blocking. "Write-capable" is generic so future Guilds inherit it: a role whose declared tool set includes a platform-known workspace-mutating tool — `write_file`, `run_shell`, or the checker tools `typecheck`/`test`, which run arbitrary commands — is write-capable. `write_plan` (run bookkeeping, not the project) and `edit_context` (conversations, not the workspace) do not count. The engine sets a run-scoped flag when such a role starts (its tool list is known from the Guild at `role_start`); in the seed Guild that is the `coder`, the only writer. The flag is conservative by construction: a false positive (counting a role that never writes) merely degrades a later park to today's blocking behavior, while a false negative would park a run that has already written. The flag rides the checkpoint like `learnedContextCeiling` does (`source/executor/checkpoint.ts`, `RunCheckpoint`), so a restart cannot reset it and park a run whose writes happened before the restart.

Mechanism — platform-initiated termination, with no LLM cooperation required. When the park rule holds, the `ask_human` handler (`source/executor/builtin-tools.ts` `createAskHuman`) does not call the human backend at all — it never registers a pending question — and instead emits the `ask_human` log event itself (so the run's own log stays a faithful record), records the question in a run-scoped park record, and marks the run to terminate. The mark is checked at every safe point, which includes between tool dispatches within the current turn as well as the loop top where `drainInterrupts` runs (`source/executor/interrupt-engine.ts`; `source/executor/engine.ts` `executeRoleLoop`); when set, the engine unwinds immediately with a platform-authored `needs_clarification` result card ("waiting for an answer to: <question>") — no further tool dispatch and no further LLM request after the mark is set, in the same turn or a later one. The between-dispatch check is load-bearing: a batched `ask_human` + `agent` call in one turn must not start the `coder` after the park decision, or the run writes after the pre-write premise was decided. The unwind mirrors the plan-modification abort pattern (`member.planAbort`, `source/executor/interrupt-engine.ts` `routeOperatorInterrupt`): the mark is run-scoped, so as each child's card propagates up the suspended `agent` calls, every role finishes with the same park card at its next check point. The run ends in `needs_clarification` with the platform-authored summary in its terminal meta; the small model is never asked to "finish gracefully" and never gets a turn to talk itself out of parking.

The `needs_input` write belongs to the settlement hook, not the park moment. The hook in the submission layer's `track` settlement path sees only the settled `RunMeta` — the run promise carries nothing else, and the engine-scoped park record never crosses to the submission layer (there is no hidden channel) — so it recovers the question by parsing the terminal meta's result summary, uniformly with boot repair. The platform park summary has the exact format `waiting for an answer to: <question>`, and its prefix is stripped to recover the question; a result summary without that prefix is a directly-finished `needs_clarification` — `validateFinishArgs` (`source/executor/builtin-tools.ts`) lets the entry role finish that status with no park, and its summary is LLM-authored — which is stored verbatim as the question. Both parse the same way and the distinction affects only the question text's cleanliness, never behavior. The park record's only jobs are to author that meta summary and drive the unwind. Crash-mid-park is safe by the same machinery: the run meta is still `running` with a valid checkpoint, so boot reconciliation resumes the run, it re-asks, and it re-parks.

What this does not change: the checkpoint stays deleted on terminal (`source/executor/executor.ts`) — parking only ever happens pre-write, so there is no work-in-progress to preserve; planning state is all that is lost. After the first write-capable role has started, `ask_human` behaves exactly as today — blocking until `/api/answer` — because pivoting mid-change would leave incoherent workspace state, and a visible stall beats silent corruption. The read-invalidation hazard this design accepts: a parked task's pre-write reads may be invalidated by the interim tasks that run before its answer arrives. That is acceptable because parking only happens pre-write — nothing but planning state exists to lose — and the briefing ("The interim briefing") forces re-verification of the premise on resume. One degradation is accepted: a run the queue does not know about (a corrupt `queue.json` read as empty, or a boot-resumed run whose item was lost) that asks pre-write parks into the void — the run terminates `needs_clarification` and the question is answerable through neither endpoint; the question remains visible in the run's history and terminal meta, and a boot re-ask of a resumed pre-write run re-parks the same way.

Foundry impact: pre-write parking changes the human-simulation contract (`docs/foundry.md` "Human simulation"). The simulator answers pending questions as an HTTP client posting to `/api/answer` — but a parked pre-write question never registers a pending entry, so the simulator never sees it: a benchmark run that asks pre-write parks (terminating `needs_clarification` with no workspace change, which fails the benchmark's validation) instead of pausing for a simulated answer and continuing. The `ask_human` log event still fires, so the `humanQuestionPenalty` term still counts the ask; what changes shape is the outcome — `eval.json`'s `humanResponses` can only serve post-write blocking questions, and a benchmark whose expected flow answers a pre-write question and continues now records a park. `docs/foundry.md` joins the documentation-updates checklist below.

## The interim briefing

Every queue-dispatched run's task text is assembled with a compact briefing, so a task queued hours ago knows what happened meanwhile: when it was queued; one line per run completed since then — enumerated with `listRunIds` and read through the run-list summary reader, each line carrying the full run id so the fast path can cite a real one, `run-<id>: <one-line summary>` (the scheduler composes the task-text fallback when a run's summary is null); queue items cancelled while it waited; and — when the item is resuming from `needs_input` — the recorded question and the operator's answer. The briefing ends with a standing instruction that the workspace may have changed since the task was queued. The run ids are not decoration: the fast-path finish format ("Already addressed by run <run id>.") demands one, and a small model asked to produce an id it was never given will hallucinate it.

The briefing reuses the continuation-briefing injection: `RunContinuation` (`source/executor/types.ts`) gains an optional `briefing` field, and `runId` becomes optional (present only when the run genuinely continues a prior run, keeping `meta.continuesFrom` honest — a first queue dispatch records no lineage because there is none). `continuationBriefing` (`source/executor/context-builder.ts`) renders the prior-run lines when `runId` is present and the briefing lines when `briefing` is, under the same depth-0 gate and in the same bracketed platform block appended below the task inside the initial user message.

Choosing this over assembling the task text at dispatch: the injection point already exists and is exactly right — depth-0 only, exactly once per run, kept out of `meta.task` (the run list and history view would otherwise render platform bookkeeping as the operator's task), and checkpointed verbatim so a resumed run never re-derives it (the property `source/executor/engine-state.ts` documents for continuations: never set on resume). For a `needs_input` resume, the scheduler also fills the continuation's `runId`/`task`/`summary` from the parked run's terminal meta (via the run-meta reader), so the resumed run is a genuine continuation of its own earlier attempt.

## Ordering, answers, and failure semantics

Answers: posting an answer to a `needs_input` item records the answer, moves the item to the front of the `waiting` list, and ticks the scheduler; the dispatch is the queue-native resume — the item's `continuesFrom` threads the parked run into the continuation, and the briefing carries the question and the answer ("The interim briefing"). Lineage follows the re-dispatch: whenever an item will run again, its `continuesFrom` is re-pointed at the just-settled run — a re-park updates it from the original parked run to the attempt that just re-parked, so an answered resume always continues the most recent attempt and never two back, and a requeue after `error` points it at the errored run, so the retry's continuation briefing carries the failure's outcome summary. Answering never preempts the active run — operator plan-modification interrupts remain the only operator-triggered mid-run abort (the park is platform-initiated). Reorder, edit of task/effort, and removal are allowed for `waiting` items only; a `needs_input` item can only be answered or left. An optional per-item `effort` overrides the project settings effort for that item's run (it rides the existing per-run effort override into `submit`); without it, the standard resolution chain applies (`source/executor/run-submission.ts` `resolveEffort`).

Failure semantics: a run ending in `error` marks its item `error` (with the terminal meta's `result.summary` and error), and the settlement tick dispatches the next item — one bad task never stalls the queue; errors surface for triage in the UI. There is no auto-retry in v1: a failed task is a triage decision for the operator, who can re-queue it in one click (the re-queue action, "UI interaction model"). The existing fatal-error teardown is distinct and unchanged: a rejected run promise tears the service down non-zero (`source/serve.ts`), leaving the queue durable for the next boot; per-run failure and service failure are different axes.

## Guild changes: the stale-task fast path

The only Guild change is a short "Queued tasks" section in `guild/prompts/orchestrator.md`. A queued task may be stale — work done since it was queued may have fixed or obsoleted it — so before planning, the orchestrator re-verifies the premise cheaply; if an earlier run already addressed the task, it finishes immediately with `status: "success"` and a one-line `Already addressed by run <run id>.` summary, citing an id taken from the briefing (the briefing lines carry the ids precisely for this). That summary convention doubles as UI vocabulary in the history view. The acceptance loop remains the per-item quality gate and bounds the cost of a missed skip: a stale bug that slips past the check passes acceptance trivially (nothing was broken), and the run costs only the check. Draft text (final wording lands when implemented):

```markdown
## Queued tasks

Your task may have waited in a queue while other tasks ran before it, and the workspace may have changed since your task was written — an earlier task may have already fixed the bug or built the feature you were asked for. The briefing below your task lists what ran while it waited, with each run's id; treat it as a hint, not proof.

Before you plan, re-verify the premise of the task cheaply, with one small delegation:

- **A reported bug:** establish the symptom still exists — a `researcher` check of the code involved, or a `coder` delegation that runs a short reproduction command.
- **A requested feature or change:** check the workspace for evidence it already exists.

If an earlier run already addressed the task, call `finish` immediately with `status: "success"` and a one-line summary of the form `Already addressed by run <run id>.` — use a run id from the briefing. Do not plan, do not delegate further work, do not change anything. If the premise holds, continue with the pipeline as usual.
```

## HTTP API

Native queue surface, all under `/api/queue`. Error semantics follow `docs/reference.md`'s HTTP API conventions: a malformed body (non-string task, unknown effort tier, non-numeric position, non-string answer) is `400` `{ ok: false, error: 'invalid_body' }`; an unknown item id is `404` `{ ok: false, error: 'not_found' }`; a status-forbidden operation (editing or deleting a non-`waiting` item, answering a non-`needs_input` item) is `409`:

| Endpoint | Behavior |
|---|---|
| `GET /api/queue` | The ordered item list with statuses. |
| `POST /api/queue` | `{ task, effort? }` — always enqueues at the tail, never 409; returns `201` with the created item; ticks the scheduler. |
| `PATCH /api/queue/:id` | Edit `task`/`effort` and/or move to a `position` — a 0-based index into the `waiting` list, out-of-range values clamped; `waiting` items only, else 409. |
| `DELETE /api/queue/:id` | `waiting` items only — marks the item `cancelled`. |
| `POST /api/queue/:id/answer` | `{ answer }` — `needs_input` items only: records the answer, moves the item to the front of `waiting`, ticks the scheduler. |
| `POST /api/queue/:id/requeue` | `error` items only — returns the item to `waiting` at the tail (the API behind the UI's re-queue action); ticks the scheduler — the common single-item case is a requeue while idle, and without the tick it would sit `waiting` forever — and re-points the item's `continuesFrom` at the errored run. |

`POST /api/runs` keeps today's external contract exactly (`docs/reference.md` "HTTP API"): when idle it dispatches immediately and returns 201 `{ runId }`; when a run is in flight it returns 409 `{ ok: false, error: 'run_in_progress' }` and enqueues nothing — scripts depend on that behavior. Internally, though, it now enqueues an item at the head — recording the request's `continuesFrom` and `logLevel` on the item — and lets the scheduler dispatch it within the same request, so every active run is queue-tracked (a run the queue does not know could never be parked, continued, or settled into the queue). A same-second `run_id_collision` that survives the tick's bounded retry surfaces as today's 409 `{ ok: false, error: 'run_id_collision' }`, and the just-created head item is removed so the caller's resubmit behaves exactly as it does today. `POST /api/answer` and `GET /api/questions` keep working unchanged for blocking (post-write) questions of the active run; parked questions are answered through `POST /api/queue/:id/answer` instead — the park path never registers a pending question in the human backend.

`GET /api/run` (the singular active-run view, `handleActiveRun` in `source/web/request-handler.ts`) keeps working with "active" meaning the active item's run — the most recently dispatched one; the head of the queue can be a `needs_input` item while a later item's run is in flight, so "head" is the wrong anchor. When nothing is running it keeps today's `lastRunId()` most-recent-run fallback so the watch screen is unchanged.

## UI interaction model

A queue panel joins the three existing screens (watch / history / compose; `source/web/static/app.js`): sections for `waiting`, `active`, `needs_input`, and recent `done`+`error`+`cancelled` (cancelled items have no section of their own — they join the recent bucket); drag to reorder `waiting` items; an inline answer box on `needs_input` items; remove/edit on `waiting` items; and an explicit re-queue action on `error` items (returns the item to `waiting` at the tail). The compose box becomes "Add task" and — with the queue universal — stops being disabled while a run is active (today's guard at `composeDisabled`, `source/web/static/app.js`). The panel's rendering is pinned to the same invariant as every other operator content (`docs/security.md` "Web client rendering pipeline"): untrusted strings — task text, questions, answers, result summaries — render through the sanitized-Markdown/`textContent` split, never as raw markup. The watch screen and history are unchanged; the history view gains nothing except the "already addressed by run <id>" summary convention appearing naturally. UI details beyond this interaction model are implementation's business.

## Module and test mapping

Per `AGENTS.md` ("Architecture"), every piece lands in its tier:

- **Pure queue logic and validation** — `source/executor/task-queue.ts`: the `QueueItem`/queue types, the `isQueueItem`/`isTaskQueue` guards, and the transformations (validate/normalize an item, enqueue at tail/head, reorder with clamped positions, remove, requeue, record-answer, map a terminal meta to an item state, repair stale `active` items from their metas, assemble the briefing lines). Fully in-memory testable: plain-object queues, fixed clocks, no filesystem.
- **Persistence leaves** — `createReadQueue`/`createWriteQueue` in `source/executor/persistence.ts`, on the `createReadProjectSettings`/`createWriteProjectSettings` pattern. Not unit-tested (thin filesystem wrappers, like the settings leaves).
- **Scheduler** — `createTaskScheduler({ readQueue, writeQueue, readRunMetaById, listRunIds, readRunListSummary, submitRun, sleep, now })` as an orchestration function in `source/executor/scheduler.ts`, no defaults; `readRunMetaById` is the run-meta reader leaf (boot repair of phantom `active` items and continuation assembly from the parked run's meta), and `listRunIds` with `readRunListSummary` are the run-enumeration leaves the briefing assembles from (completed runs since `queuedAt`; the reader returns each run's `summary` — null when none — alongside its `task` field, and the scheduler composes the task-text fallback itself). Tested with a fake `submitRun` (recording calls, returning scripted `SubmitResult`s), a plain-object queue store, fake run-meta/run-list readers, and a fake `sleep`/`now`: dispatch-on-idle, no-op-when-busy, dispatch-marker written before `submit` and restored to `waiting` on `run_in_progress`, bound-or-released at boot (with the resumed `running`-meta scan), the with-`runId` resumed item left untouched, collision retry re-reads after the fake sleep, park ordering, answer-front dispatch with `continuesFrom` threading, lineage re-pointing on requeue and re-park, `logLevel`/`effort` threading, error mapping, boot repair from a terminal meta, interrupted-to-waiting re-dispatch, and the shutdown gate suppressing dispatch while still mapping the settled item.
- **Settlement hook** — `createRunSubmission` gains a required `onRunSettled` dependency invoked from `track`'s fulfillment branch; `source/executor/run-submission.test.ts` covers that it fires exactly once per settled run and never on the rejection branch.
- **Park mechanism** — the run-scoped write-capability tracker and park mark inside the executor's ask-handler path, checked at the loop top and between tool dispatches (`source/executor/builtin-tools.ts`, `source/executor/engine.ts` `dispatchToolCallSequence`/`executeRoleLoop`, checkpointed via `source/executor/checkpoint.ts`); `source/executor/engine.test.ts` exercises park-vs-block through fake handlers and a fake `humanBackend`, in memory — including a batched `ask_human` + `agent` turn where the park mark must prevent the `coder` from starting.
- **Briefing injection** — the `RunContinuation` extension in `source/executor/types.ts` and rendering in `source/executor/context-builder.ts`; `source/executor/context-builder.test.ts` covers the block's placement and the depth-0 gate.
- **Endpoints** — the `/api/queue` routes in `source/web/request-handler.ts`, with the queue leaves and scheduler in `RequestHandlerConfig`; handler tests inject fakes exactly as the existing route tests do.
- **Wiring** — `source/serve.ts` constructs the leaves, scheduler, and settlement hook, orders reconciliation before the first tick, and flips the scheduler's shutdown gate when the signal arrives. Not unit-tested (integration glue).

Interactions, explicitly: `run_id_collision` — handled inside the tick's bounded, sleep-past-the-second retry ("Dispatch and the scheduler") and surfaced as today's 409 on the `POST /api/runs` path; the loop detector — per-run machinery whose abort ends the run in `error`, mapping to the item's `error` and the next tick, unchanged; operator plan-modification interrupts — per-run machinery, unchanged, and still the only operator-triggered mid-run abort (the park is platform-initiated; the queue never touches an active run).

## Decisions and rejected alternatives

- **Always-on universal queue** (D1) — one code path, one mental model; the operator's rule is "assume the user always walks away after submitting". *Rejected:* an interactive-vs-queued mode toggle — queue membership is universal; a toggle would fork every path (submit, park, briefing, UI) for behavior the queue already makes identical.
- **Git-stash parking** — deferred, not rejected forever. v1 parks only pre-write, where there is nothing to stash, so the platform-initiated termination suffices; revisit only if mid-work questions prove common enough that blocking on them is a real cost. Mid-write parking would need workspace capture/restore (stash or snapshot) with all its coherence hazards.
- **Per-task worktrees/branches** — rejected: the workspace-model change is large (every tool, the in-place contract, and the foundry's assumptions assume one tree), and only multi-agent parallelism would want it — which is not a goal.
- **Timeout-then-park** — rejected: N is unknowable (a planning question may legitimately take minutes of thought), and an arbitrary timeout either fires on healthy runs or never fires; a run that silently parked itself after an arbitrary wait erodes trust. Parking is keyed to a structural fact (pre-write), not a guess.
- **Queue-time duplicate detection by text similarity** — rejected: the stale-task fast path ("Guild changes: the stale-task fast path") checks the premise against the real workspace at run time, which is strictly better than fuzzy text matching at enqueue time; similarity search also cannot tell "same bug" from "same words".
- **LLM queue-management tools** — rejected: the platform does bookkeeping perfectly and for free; queue tools would spend tokens and trust on work that is infrastructure. The Guild stays unchanged except for the prompt in "Guild changes: the stale-task fast path".

## Open implementation details

Deliberately left to implementation: the finalized JSON schema of `queue.json` (field names and optionality beyond the shape in "The queue: storage, item model, state machine"); the drag-reorder mechanics in the panel (pointer vs. keyboard affordances, optimistic vs. confirmed reorder); the queue size bound and pruning policy for `done`/`error`/`cancelled` items (a bound keeps the file small; pruning must never drop `waiting`/`active`/`needs_input` items); the exact cap on briefing lines for long queues; and the final wording of the prompt in "Guild changes: the stale-task fast path".
